# Deck

Part of Leaf's spec (see `AGENTS.md` for the index).

### Deck Embed

`[[deck]]` on a line by itself embeds the full Deck app (see Deck) inline, using the same placeholder pattern as `[[toc]]`. Syntax: `[[deck param=value param2=value2]]`.

| Parameter | Values | Default | Description |
|-----------|--------|---------|-------------|
| `tag` | comma-separated tags | — | Pre-filters by tag. Comma = AND, pipe `a\|b` = OR, a leading `-` excludes (`tag=work,-mary`). The chips are locked (the page says what it shows); new tasks get the single tags, but a task's tags stay editable. |
| `view` | `focus`, `open`, `plan`, `completed` | Focus (or the tab remembered this session) | Opens on that tab on every load; a URL `?view=` overrides it. Old names are still accepted via `_FILTER_ALIASES` (`upcoming`, `today`, `all`, `backlog`, `due`, `done`), as is `filter` for `view`. |
| `limit` | integer 1–99 | none | WIP limit: Focus warns at this many tasks, and Plan day sections with at least this many are flagged amber. `?limit=N` works on `/deck`; `capacity` is an old alias. |
| `list` | a tag | — | Makes the embed a separate list: it shows the tasks with that tag, the tag is locked there and marked as a list everywhere (see Deck → Separate lists). Cleaned like tags, lowercased (`clean_list`). |
| `compact` | `1`/`true`/`yes` | — | Every tab of the embed starts in one line per task (otherwise only Open and Completed do; see Deck → Compact); the viewer's own switch, once used, wins. |
| `keep` | `1`/`true`/`yes` | — | New tasks created in the embed are keep tasks (the edit modal's checkbox starts checked), e.g. a shopping list of staples. |
| `home` | `1`/`true`/`yes` | — | Makes this embed your own deck, the **deck's home**: the Deck module links go to its page, the page belongs to the Deck module, New adds a task in this embed, and the due count counts what it shows (see Modules). The first page A–Z with one wins; without any, the Deck links go to `/deck`. |
| `labels` | up to 3 comma-separated names | `Open,Plan,Focus` | The embed's own names for the tabs, in on-screen order, e.g. `labels=Catalogue,Plan,Shopping` for a shopping list. Only the words change: views, `view=` values and links keep their names. An empty entry keeps the default, `_` stands for a space (params split on whitespace). Rendered into the tab buttons by `build_deck_embed`; `deck.js` reads them back (`tabLabel`) for the "← Back to …" link, the limit warning and the ⟲ tooltip. |

```markdown
[[deck]]
[[deck tag=urgent view=plan]]
[[deck view=open]]
[[deck list=groceries tag=weekly]]
[[deck view=focus limit=5]]
[[deck list=groceries keep=1 labels=Catalogue,Plan,Shopping]]
[[deck list=task view=focus limit=8 home=1]]
```

**Headless instance**: `build_deck_embed(params, headless=True)` renders the app hidden, for pages that only need its edit modal (the editor's Make task, see Task references). `openEditModal(null, opts)` takes, besides `tags`, a starting `title`, `description`, `start_date` and an `onCreated(task)` callback; `titles` instead of `title` is batch mode (one task per title, the fields shared, `onCreated` gets the array).

**Implementation** (`decksyntax.py` for the syntax, `deck.py` for the HTML): `DECK_RE` finds the directive and `parse_deck_params()` parses its `key=value` pairs. `process_deck_embeds()` swaps each one for a numbered placeholder before rendering, and `inject_deck_embeds()` replaces each `<p>PLACEHOLDER</p>` with `build_deck_embed()`'s HTML (`templates/deck_embed.html`) afterwards. The embed passes its params as `data-init-*` attributes; it carries no script: `deck.js` (an ES module `leaf.js` imports on every page) starts every `.tasks-app` on load (`initDecks`, marking each `data-ready`). Element ids get a `-<n>` suffix after the first embed, so a page can hold several. `deck.js` also reads `?tag=`, `?view=`, `?search=`, `?task=`, `?new=1` from the URL; `?new=1` opens the new-task modal in one embed only, the deck's home if the page has it, else the first.

The deck itself is `/deck`; embeds are for custom views on ordinary pages (a tag deck, a list with notes around it). Nothing links to a `deck.md` page.

**Task ↔ page linking** is a `[[wikilink]]` (or `/page/` link) in the task's title or notes, which lists the task under the page's "Linked tasks". The other way round, a page shows one task inline with `[[task:<id>]]` (see Task references). There is no `page` field: `page` in embeds or API bodies is ignored.

## Deck (Task App)

A task app at `/deck` (a built-in page, `deck_page()`), also embeddable via `[[deck]]` (see Deck Embed). Server side is `src/deck.py` (a Flask Blueprint: `/api/deck/*` routes, the embed's HTML, `deck_counts`) on top of `src/deckstore.py` (the files and the task model: storage, recurrence, history, comments, task backlinks, search docs) and `src/decksyntax.py` (the syntax in page text). Client side is `deck.js` (DOM, one instance per embed) plus `deck-core.js` (pure logic, tested under Node).

Several embeds per page work: each instance keeps its own task array, and a write in one refreshes the others (`refreshOtherInstances`). Every instance also reloads on `visibilitychange` and bfcache `pageshow`, so a tab left open for days shows current tasks and today's day sections. `refreshIfIdle` skips the reload while a drag, swipe, completion grace period, inline edit, ⋯ menu or edit modal is in progress. There is no polling.

### Storage

- The deck's files live in the `_deck/` folder (`deckstore.DECK_FILE` and paths derived from it): open tasks in `tasks.json`, completed ones in `completed.json` (flat JSON arrays, committed to git on change). Completed tasks from earlier years live in `completed-YYYY.json` (only that exact name is an archive). `_atomic_write` creates the folder, so a new wiki gets it on the first write. Write routes read every completed file (`read_completed_all_strict`) and `_write_completed` files each task by its completion year, writing only files whose content changed; startup does the same split (`archive_old_completed`) for a year change without writes. So archived tasks can be edited, reopened, deleted, tagged and restored like any other; Completed shows them by year (see Views).
- All mutations go through a module lock (`_LOCK`) and atomic writes (temp file + `os.replace`); the dev server is threaded. Write paths use a strict reader that raises `DeckCorrupt` (503) on an unreadable file instead of treating it as empty and wiping every task.
- Request bodies are validated (`_json_object`, `_as_str`, `_as_int`, `_as_str_list`, `_id_list`): bad input is a 400 with JSON `{ error }`, never a 500. Numeric strings are accepted for integers; `tags` may be a comma-separated string.
- Reads clean the tags (`_normalize_list`, `clean_tags`), since a file edited by hand may have `"local llm"` or `#work`. Older data formats are no longer converted: the conversions (deck files in the wiki's root, completed tasks in `tasks.json`, `focus_date`/`defer_days`/`recurrence.anchor`/`page`/`focus_order`, spawns without `spawned_from`) were removed in 2026-10. A wiki last used before then must be opened once with an earlier Leaf (git history) first.

### Dates

A task has two independent dates; changing one never moves the other.

- **`due_date`**: the deadline. Only a past due date makes a task overdue.
- **`start_date`**: the day the task becomes available, and the commitment to work on it. Having one makes a task *planned*. A past start date is not overdue, it means "available since" (cards show "since Sep 21").

**A start after the deadline** is usually a slip, but not always (a late task planned for next week), so it is never forbidden, only questioned. Every quick way to set a start date (the Plan board, ⋯ Start today/tomorrow and Pick start date, the card's 📅 picker, **f**/**F**; `setStart` and the picker go through `startsAfterDeadline` → `planOnDay`) asks "Move the deadline too?" (`confirmDeadlineMove`): Move deadline sets both dates, with undo; Cancel writes nothing. Outside the board, an overdue task started today doesn't ask: that is catching up on a missed deadline (swiping right never asks for that reason). The board does ask then, since the card would otherwise stay in Overdue. The edit modal shows a hint under the dates instead (`syncDateWarning`): "Starts after its deadline", with a button that moves the other date (the deadline, or the start when Due was moved before it). It doesn't block saving.

The edit modal's "Days before due" is just another way to enter the start date (`start = due − N`) and is not stored. Recurring instances keep the gap between the two dates, but a new instance's start date is never before today (it can't have been available before the previous one was done); when that clamps it, the series remembers the gap in `recurrence.lead` for the next instance.

See History. |

### Views

A segmented control (`.view-tabs`, one `<button data-filter>` each) in the order **Open · Plan · Focus** (`data-filter` `open`/`due`/`focus`). **Tab**/**Shift+Tab** cycle them. Initial view: URL `?view=` > embed `view=` > tab remembered in `sessionStorage` (plain embeds only) > Focus. On phones the control spans the full width.

- **Open**: every open task, in two sections: **Unsorted** (no `sort_order`, newest first; new tasks land here) above **Sorted** (manual order). Open has no filter for unplanned tasks (an "Unplanned" toggle was removed): those are the Plan board's Unplanned section, where dragging to a day plans them. So Unsorted means "not yet ranked" and Unplanned "not yet scheduled", each with one home. A leftover `unplanned=` embed param is ignored.
- **Plan** (`due`): a day board grouped by `DeckCore.bucketKey`: Overdue (`due_date < today`, display-only), Today, Tomorrow, the next weekdays, Later, Unplanned (no start date; nearest deadline first). Later and Unplanned always show. Dropping a card on a day sets its start date, on Unplanned clears it, on Later opens a date picker (min today+7). An empty section is only its dashed header row (min 1.9rem, 2.5rem on coarse pointers), which takes the drop; nothing grows when a drag starts. Day headers show a count and turn amber at the limit. The board only decides the day: inside a section tasks are in Open's order (`DeckCore.byOpenOrder`, shared with Open), except Overdue (by deadline) and Unplanned (nearest deadline first, then Open's order). A drop within a task's own section, on a task or on its heading, does nothing; to reorder, use Open or Focus. The one exception is Later's heading, which opens the date picker to choose another later date. A drop on a day after the task's deadline (`planOnDay`) would leave an overdue or due-today card where the deadline puts it, so it asks "Move the deadline too?" (`#task-deadline-modal`): Move deadline sets start and due to that day, with an undo toast restoring both; Cancel writes nothing. Wiring: `setupBoardDragAndDrop` per card plus list-level handlers attached once.
- **Focus**: what you're working on now (`DeckCore.isFocus`: `start_date <= today`, or due today/overdue; the board's Overdue + Today). It is Open filtered: the same sections (Unsorted · Sorted) and the same order (`byOpenOrder`), so there is one manual order, and ordering on Focus orders Open. That fits a shopping list: Open is the shop's order, Focus today's list, and an item added on Focus (Unsorted) is dragged into place among today's items, which places it in the shop's order (see Sections). Due and overdue tasks have no section of their own: they keep their place in the order, marked by their deadline colour. The Deck links (with the due count) open here unless another tab was used this session. With a limit, a warning shows when Focus reaches it. Empty Focus says "Nothing planned for today" and links to Plan. New tasks created here get today as start date. (Focus once had its own order, the Lineup (`focus_order`) above Others; it was removed as a second commitment on top of the start date.)
- **Completed** is not a tab but a link under the list (`#task-completed-link`, `✓ Completed (N) →`, count from `/api/deck/completed-count`, refreshed after every write). In Completed, the link reads `← Back to <tab>`, naming the tab it returns to. While filtering another view it counts the matching completed tasks instead (`✓ 2 matches in Completed →`, no number while loading). `/api/deck` returns open tasks only, so completed tasks are fetched on demand (`fetchCompleted`, one request at a time); `deckGen` refetches if `fetchDeck` replaced the list meanwhile. Completed's heading has a **year switcher** (`.completed-years`, years from `/api/deck/completed-years`, shown when there is more than one) for the yearly archives; `?year=YYYY` opens that year (search links to archived tasks carry it), and going back to a tab returns to this year (`setCompletedYear`).

**Sections** (Open and Focus; `SECTIONS`, `sectionHTML`, `.list-section[data-section]`): Unsorted (no `sort_order`, newest first) above Sorted (`sort_order`). Moves treat both headings as slots in the visible list (`sectionList`, `applySectionList(list, moved)`): which side of the Sorted heading a task lands on decides its section; a task dropped on a task lands where the pointer is: above it on its upper half, below it on the lower half, from Unsorted and within Sorted alike, a line on that edge showing it while dragging (`dropSide`, `.task-drop-before`/`-after`, mouse and touch; `sectionDrop`); dropping on the Sorted heading moves the task to its top; reordering within Unsorted does nothing; leaving Sorted sets `sort_order` to `null`. Ctrl+Shift+↑/↓ moves one slot, headings counting. Only the moved tasks change place in the full order: each goes right after the visible task now above it (or right before the one below, when first), and every task the view or filter hides keeps its place. So on Focus, sorting in one item never shuffles the catalogue around it. Every save renumbers the whole order densely.

**No hiding**: every open task is always reachable from its own deck (Open or Plan) and from search. Dates decide where a task appears, never whether.

### Interaction

- **Filter field** (`#task-filter-search`, `DeckCore.parseFilter`/`matchesFilter`): `#words` filter by tag (all must match; `#a|b` = any), `-#word` excludes a tag (`-#a|b`: neither), the rest searches title and notes. `/` focuses it, `#` focuses it and starts a tag. Typing a `#word` (or `-#word`) suggests tags of the tasks the other tag words leave visible (free text is ignored for this). Embed `tag=`/`?tag=` become a query via `DeckCore.tagParamToQuery`. New tasks get the filter's single tags.
- **Tag chips** (`chipField` in `deck.js`): in the filter field and the edit modal's Tags field a completed tag becomes a chip in front of the typed text (`.chip-input` box wrapping the input, `.tag-chip`). A chip can't be edited, only removed: Backspace at the start of the field removes the last one, its × any. Filter chips are whole filter words (`#a`, `-#b`, `#a|b`); the query is the chips plus the text (`filterQuery()`), and `?tag=`/`[[deck tag=…]]` arrive as chips. In the Tags field a completion or a comma (typed or pasted) makes a chip, with no `, ` left behind; Save takes the chips plus a half-typed tag (`editTags()`). The dropdown hangs under the whole box.
- **Tag completion** (`attachTagAc`: filter, Tags field, title `#tag` shorthand, bulk tag dialog `t`/`T`): ranked by `DeckCore.rankTags` (exact, prefix, substring, in-order letters; then usage count, then A–Z). The best match is pre-highlighted so Tab/Enter completes it; Esc closes only the dropdown. Keys are handled in the capture phase. The dropdown is appended to the field's parent, since in a `<dialog>` only the top layer is visible.
- **Bulk tags** (`openBulkTagModal`, `.bulk-tag-modal`; **t**, or **T** to remove, on the selected tasks): the dialog lists every tag the selection carries (`DeckCore.selectionTags`, case ignored, most common first), each a three-state box (`role="checkbox"`, `aria-checked`): on every task ✓, on some – ("2 of 3", left as it is), on none (struck through, the tag goes). A click or tap cycles all → none → some, back to some only where the tag started so. The field below adds tags as chips (`chipField`; completion from every tag in use, minus those every selected task has; a comma makes a chip). Opened with T, the field has no chips: it completes to the selection's own tags and turns the completed one off. Enter or Apply sends only the changed rows plus the typed tags (`DeckCore.bulkTagChange`) in one `batch-tag` request, a half-typed tag included; nothing changed sends nothing. The toast names the change ("#work added to 3 tasks", "#old removed from 2 tasks", else "Tags changed on N tasks"; counting only tasks whose tags changed), or where tasks went if the change took them out of the view; its Undo puts back each changed task's tags in one `batch-update`. On touch the field is not focused while there are rows to tick, so the keyboard waits until it is tapped.
- **Quick-add** (new tasks only, `DeckCore.parseQuickAdd`): trailing shorthand like `Call Bob tomorrow #work due:fri`. Start: `today`, `tomorrow`/`tmrw`, a weekday (next one, never today), `+3`/`+3d`/`+2w`, `YYYY-MM-DD`; due: `due:` + the same; tags: `#tag` starting with a letter. Only trailing words count, and shorthand that would empty the title is ignored. `#task-edit-quick` previews the result; shorthand wins over the date fields.
- **Completing**: the checkbox completes after a cancellable grace period. Completing a recurring task spawns the next instance, stepping from the previous primary date (or today with `from: completion`) until ≥ today, with its start date not before today (see Dates); month steps clamp to the month's last day. Un-completing removes the spawned instance.
- **Checkboxes in notes**: a `- [ ] item` line (`*`/`+` too, `[x]` ticked) renders as a real checkbox in the card's notes (`renderDesc`). Ticking it flips the line in the description and saves (`DeckCore.toggleDescCheck`, which numbers items with the same `DESC_CHECK_RE` the renderer uses). The task's own checkbox is `.task-checkbox input`, so the two never mix. In the edit modal's notes, Enter continues a list exactly as in the page editor (`continueList`, imported from `js/util.js` like `pasteUrlAsLink`): after `- [x] eggs` it starts `- [ ] `, and Enter on an empty item ends the list.
- **Won't do** (⋯ menu; cards have no ✗ button any more) archives without spawning; **Skip** (⏭, recurring only) archives as won't-do and spawns the next instance. Both show an undo toast; reopening a skipped entry removes its spawn.
- **Delete** (`deleteWithUndo()`, from keyboard, modal or menu) confirms, then offers undo via `/api/deck/restore` with full snapshots.
- **Planned cue**: a planned task's card gets a coloured left edge, the same on every tab for consistency: amber when it is in Focus already (start today or earlier), blue when planned later (`task-planned-now`/`-later`). On Open it tells decided tasks from undecided ones without changing the order. A due/overdue urgency colour wins. The 📅 date is coloured too: blue for a later start, amber for today, plain for a past start ("since …", never a warning).
- **Inline dates**: the ⏰ (due) and 📅 (start) chips open a date picker. **f** starts the selected task today, **F** tomorrow (again clears).
- **⋯ menu** (the `.task-menu-btn`, always shown, three dots drawn as an SVG (`MORE_ICON`) so they sit on the line's centre in any font; also **right-click** on a card, `openTaskMenu(id, anchor, {x, y})` at the pointer, selecting the card, a link in the card keeping the browser's menu; from the keyboard the menu key or **Shift+F10** on the selected card): all card actions (Edit…, Start today/tomorrow, Pick start date…, Unplan, Skip, Won't do, Delete…; for completed tasks Edit…, Reopen, Delete…). A popover with ↑/↓/Enter/Esc on desktop (deck shortcuts suspended while open), a bottom sheet at ≤640px.
- **Edit modal**: double-click or Enter on desktop; on touch the first tap selects the card (in compact view also expanding a task with more to show, see Compact) and a tap on the selected card opens it (`pressedSelected`, noted at `pointerdown`, since touch's compat mousedown selects before the click; pointer type of the last `pointerdown`; a double tap's `dblclick` is ignored, so it never edits the title in place), or Edit… in the menu. Centred with `inset: 0; margin: auto` and **no transform** (a transform would clip `position: fixed` popups like the date picker), scrollable, sticky action bar. At ≤640px full screen with Due | Start and Repeat | Every | From done on shared rows (`.task-row-dates`, `.task-row-repeat`). The List field sits in a closed `<details>`; saving a task into another list removes it from the view with a notice.
- **Date picker** (`openDatePicker`): a row of shortcuts above the month, counted from today, not from the current value: **Today**, **Tmrw**, **+2d**, **Mon** (next Monday), **+1w** (`QUICK`, `.dp-quick-btn`; short labels so all five fit one row, the accessible name and tooltip say it in full, e.g. "Next Monday: Mon, Oct 5"; below the month only Clear; the current value marked, ones before the picker's `min` disabled). They commit like a picked day, so the card's 📅 asks about the deadline as usual. Positioned after every `draw()` (below the anchor, else above, else inside the window; never past a screen edge). A press outside only closes it: `pointerdown` in the capture phase, then `swallowNextClick` eats that press's mouse/click events, so a tap can't also hit what's underneath.
- **`?task=<id>`** selects, scrolls to and flashes (`.task-flash`) that task; a missing task gets a notice. A newly created task is flashed the same way when the view shows it.
- **Rejected writes** show the server's error as a toast (`showNotice`).
- **Toasts and modals** (`placeToast`): a toast shown while a modal dialog is open goes into the dialog, since in `<body>` it would sit under the dialog's top layer and its Undo couldn't be clicked (deleting a comment showed that); when the dialog closes the toast moves back to `<body>`.
- **Cards** (`taskHTML`, style.css "Cards"): one layout for every card. The first line: checkbox, title (as wide as it needs, at least 6rem, 4.5rem on phones; it wraps), the tags right after it (pills), markers and dates at the right end (`.task-meta` sits in the line), ⋯ last. **Nothing jumps on hover**: what is always shown (markers, 📝, 💬, dates, ⋯) ends at the right and stays put; what hover adds (⏭, the empty ⏰ 📅) appears left of it (first in `.task-meta-right`, CSS `order`). A task with notes shows 📝 (`.task-has-notes`) on every card, since a compact line hides the notes. Under it the notes, then the latest 3 comments, newest first (`.task-card-comments`; "N earlier…" opens the modal at the comments). Full cards (and the expanded task) show every tag: short of room, the tags wrap onto more lines under the first, the widest one counting toward the meta column (so the title wraps sooner), the dates staying at the first line's right end. A compact line, one line by definition, lets tags give way instead, first and only whole (they wrap onto a second line that the one-line height hides; an empty `::before` lets even the first one go); dates and markers are never clipped: the meta column's minimum is their width (`white-space: nowrap`, so "📅 Tomorrow" counts as one piece) plus the widest tag's, so a compact line keeps room for one tag and expanding it moves nothing. The first line has one fixed height (`--line`, the compact row's), so a full card's first line sits exactly where a compact line's does. Empty date placeholders (⏰ 📅 to set one) show on hover, left of the dates (full cards and compact lines; in a compact line whose title is cut off, the tags move over to make room), and always in full cards on touch. A double-click anywhere on a card but its title (which edits the title in place) and its controls opens the modal. **Phones** (≤640px): the line is too short for title and dates, so the title has the first line to itself (beside the checkbox and ⋯, which keeps its finger-sized target without making the line taller), tags, markers and dates go to a second line with the card's whole width, and a card with none of them stays one line; compact lines the same, rows ≥44px as a whole. There every tag shows: the tags flow in that line (`display: contents`) and wrap onto more lines rather than drop out, the dates following the last tag at the right end, or on the next line when they don't fit beside it.
- **Compact** (`applyCompact`, `.deck-compact`): every card but the expanded one collapses to its first line (title cut off with …, notes and comments hidden; 📝 says a line has notes). **Per tab**: Open and Completed (long lists to scan) default to compact, Focus and Plan (a task's details matter) to full cards (`COMPACT_DEFAULT`); `[[deck compact=1]]` makes every tab start compact. Rows stay ≥44px on touch. Switched by the density button in the toolbar (`#task-density-btn`, `aria-pressed`) or **v**, remembered per deck and tab in `localStorage` (`leaf-deck-compact:<path>|<list>|<tag>|<instance>|<view>`, `compactFor`), so it survives reloads. **Expanding a task** (`expandedId`, `setExpanded`, `.task-expanded`): one task at a time looks exactly like a full card, so its line doesn't move. Selecting a task (a click, arrows, j/k; `setSelected`) expands it, the previous one closes, so you can read through tasks; **Enter** opens the modal, as on full cards. On touch the first tap selects and expands, a tap on the selected task opens the modal. Only a task with more to show than its line expands (`hasMore`: notes, comments, or a title the line cuts off); one without stays a line (on touch the first tap only selects it). **Esc** collapses it (the next Esc clears the selection) until another task is selected; several selected or none close it too. It survives re-renders (`taskHTML` adds the class); switching density resets it. Double-click still opens the modal directly.
- **Header**: tabs, filter, the density button and **+ New** on one line on desktop (`.tasks-toolbar` `flex: 1 1 20rem`), two lines on phones with a label-less "+" (accessible name "New task").

### History

The server logs events on the task (`log_event` in `deckstore.py`): `created` (create and recurring spawn; a new task's first dates are not changes), `start`/`due` whenever the date actually changes (`_apply_task_fields`), `done` (also for a keep task, whose cleared start date is part of it), `reopened`, `wontdo` and `skipped`. A recurring task's next occurrence carries the series' history on (with the `done` or `skipped` just logged) plus a `repeat` entry ("Repeats: next Oct 3"), so the series reads as one log; it gets no `created` of its own. Only these; title, tag or order edits are not logged. Undo must not leave a trace, so every undo that PUTs old fields also sends the task's old `history` (`oldHistory` in `deck.js`: start-date, won't-do, skip and keep undos), and the server applies a sent `history` last (`clean_history` validates it), replacing what that request logged. Restore snapshots keep it too. Reopen-undo and bulk-complete-undo go through `batch-complete` and do log (`done`/`reopened`).

The edit modal shows it in a closed **History** section (newest first, with a count), (`.task-edit-extras`). Creation is the oldest entry; tasks from before the log get one from `created_at`. There is no separate "Created:" line.

### Comments

Quick status lines on a task ("called Bob, waiting", "Alex: 6 people"), in `comments` (`[{ id, at, text }]`, oldest first; `id` 8 hex chars, `at` `YYYY-MM-DDTHH:MM`, text up to `COMMENT_MAX` = 2000 chars). Not part of the History: they are never capped, undo of other changes never touches them, and adding one logs no event.

- **Routes**: `POST /api/deck/<id>/comments`, `PUT`/`DELETE …/comments/<cid>`, each returning the task, for open and completed tasks alike (`_find_for_write`). `PUT /api/deck/<id>` with `comments` replaces the whole list, for undoing a delete; `clean_comments` validates it (and restore snapshots), dropping bad entries and renumbering duplicate ids.
- **Edit modal** (`renderComments` in `deck.js`): a Comments field under Notes, hidden for a new task, with the list newest first. Enter (or Add) saves a comment at once, not with Save, so Cancel never loses one. ✎ edits one in place (Enter or leaving the field saves, Esc cancels without closing the modal), × deletes it with an undo toast.
- **Cards**: a `💬 N` button (`.task-comments-btn`) in the meta row (an expanded compact task also lists the latest 3, see Compact); its tooltip is the latest comment with its time, a click opens the modal with the comment field focused (`openEditModal(id, { focusComment: true })`).
- **Carried on**: a recurring task's next occurrence takes the series' comments with it, like the history.
- **Search and MCP**: comment text is part of a task's search text (`task_search_docs`, so semantic search too), a comment counts as activity for `edited:`/`after:`/`before:` (`last_activity`), and `_mcp_task_text` lists them after the notes under "Comments:" (`- YYYY-MM-DD HH:MM: text`).

### Keep tasks

A task with `keep: true` is never archived: ticking it off means "done for now, back to the pool". It suits a shopping list used with the deck's views: Open is the catalogue of staples, starting items today puts them on Focus (the actual shopping list), and ticking one off sends it back to Open. Completing a keep task (`keep_done`, in `PUT` and in `batch-complete`) clears its start date and its deadline, and sets `last_done` to today; it stays in `_deck/tasks.json` with the same id, tags, notes and place in Open's order, and Completed stays empty. Since Completed can't reopen it, the card shows an undo toast that restores the old fields (`keepSnapshot`). **Won't do** and **Delete** retire a staple. Keep and Repeat both say what happens after done, so they exclude each other: `keep` clears `recurrence`, and the edit modal disables Repeat while "Keep after done" is checked. Cards mark keep tasks with ⟲ (`.task-keep`). `[[deck keep=1]]` makes new tasks keep tasks.

### Separate lists

A separate list is a tag that a page declares with `[[deck list=<tag>]]`: a higher-order tag, nothing more. It gets a home page (its view's params, where links to its tasks open) and a marker, but otherwise behaves as a tag; in particular the main deck shows its tasks like any other (it once hid them, with a "Show separate lists" checkbox to bring them back; removed 2026-10, since the main deck is the view of all tasks you filter). There is no `list` field (an old stored one is ignored); a task is in a list by carrying its tag.

- **Declarations** (`pages.deck_lists`; `deck.py` and `pages.task_list` read it): every page is scanned for `[[deck list=…]]` outside code (`page_deck_lists`, kept in `_page_meta_cache`, so by mtime), giving `{name: {slug, title, params}}`. When several pages declare one, the first slug A–Z is its home. A tag no page declares is an ordinary tag (`/deck?list=<tag>` still shows its tasks, with a note saying no page declares it). Editing the declaration away ends the list at once.
- **A task's list** (`pages.task_list`, mirrored by `taskList` in `deck.js`): the first (A–Z) of its tags that is a declared list. Links to a list task (search, Linked tasks, task chips, MCP) carry `&list=<name>`; on a page that declares a list the task is in, its chips and Linked tasks use that list instead (`render.link_list`), so a task in two lists (`#presentideas #task`) opens in the list the page is about. A chip re-rendered after ticking keeps it: `js/page.js` sends the page's list embeds as `/api/preview?lists=…`. And `/deck?list=<name>` renders with the declaring embed's params, so the list looks the same everywhere.
- **Scopes** (`decksyntax.in_scope`, `inScope` in `deck.js`): a list view shows its tag's tasks; the **main deck** (an embed with neither `list=` nor `tag=`, including `/deck`, URL `?tag=` notwithstanding) shows every task, list tasks included, as do a `tag=` embed (a `#task #sam` task belongs on a Sam page whatever lists exist), the main Completed count and, without a deck home, the due count.
- **Locked filter**: an embed's own filter words (`list=` and `tag=`; `embedFilterWords`) are chips without × (`chipField`'s `locked`, `.tag-chip-locked`; Backspace skips them), so the page always shows what it says and new tasks get its single tags. A URL `?tag=` stays removable. In the filter, the edit modal and on cards a list's tag comes first and is marked as a list: a list icon (an SVG mask in CSS `::before`, `--list-icon`, in the accent colour; so the text stays `#name`, what you type), a faint blue tint and a tooltip naming its home page ("List: Shop", `listTooltip`; titles from the embed's `data-list-homes`, `deck_lists`' `title`). Other tags (locked or not) stay plain (`listWord`, `.tag-chip-list`; `.task-tag-list`). A task's tags are never locked: swapping `#groceries` for `#hardware` in the edit modal or with bulk tag (`t`/`T`) moves it to another list. A save that takes a task out of view says where it went: "Saved to list “…”." when it left for a list (`listMovedNotice`), else "Saved; it no longer shows here." (`leftViewMessage`). Both are undo toasts (`offerUndoLeave`): undo PUTs back everything the save could change (`editSnapshot`: fields, order, recurrence and the old history, so no trace) and reloads the deck, since the task left `tasks`. Bulk tag moving tasks out gives one toast ("2 tasks saved to list “…”.") whose undo restores each one's tags. A new task created out of view only gets the notice.

### Touch

- With a mouse (`hover: hover`) ⏭ shows only on hover, for the selected card, or with focus inside, left of the dates (right-click opens the menu too); under `(hover: none)` ⏭ is hidden (the ⋯ menu has it); ⋯ is always shown; under `(pointer: coarse)` buttons, checkboxes and chips get finger-sized targets, fields use 16px text (no iOS zoom), and cards can't be text-selected.
- **Long-press drag**: 350 ms without moving over 10px picks a card up and selects it (without scrolling). A floating copy (`.task-touch-ghost`) follows the finger, the page auto-scrolls near the edges, and release drops through the same code as a mouse drop (`touchDrop` adapters registered by each render; list touch listeners attached once). A touch `pointerdown` sets the card's `draggable` to false (mouse sets it back; cards are marked `data-drag`), and native `dragstart` is cancelled for touch, because Android Chrome and iOS Safari otherwise start their own HTML5 drag mid-gesture. Moving earlier is a normal scroll; a finished drag isn't a tap.
- **Swipes** (`swipeActions`; they may start on a date chip, which sits on the first line where a thumb starts, a mere tap still opening its picker) only move tasks in and out of Focus: right = start today (Open, Plan), left = clear the start date (Focus, Plan). No action, no movement (e.g. right on a Focus task, left on an unplanned or due task). A mostly sideways move (|dx| > 1.5·|dy|, over 10px) drags the card and reveals the label (`data-swipe-label`); past `min(110px, 30%)` it arms (`.task-swipe-armed`), and release runs `setStart` with an undo toast. Cards have `touch-action: pan-y` and `.tasks-list` `overflow-x: clip`.
