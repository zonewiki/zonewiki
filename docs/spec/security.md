# Security

Part of Leaf's spec (see `AGENTS.md` for the index).

How Leaf protects the wiki: the login gate, the MCP token, the Host and Origin checks, framing, HTTPS cookies and throttling. Each rule has tests in `tests/test_routes.py` or `tests/test_mcp.py`, and `go/security_test.go`.

- Optional password auth: `./run.sh config passwd` (a hash as `password` in the settings file, `.leaf/config`) enables a login gate. If unset, no auth is required. Leaf makes a key once and keeps it in `$LEAF_DATA/.leaf/secret_key` (mode 0600, listed in `.git/info/exclude` so it never reaches git or a git remote; `secretKey()`), so restarts don't sign anyone out. A wiki folder Leaf can't write to gets a new key per start. Routes `/login` (GET/POST) and `/logout` (POST) handle the session. A "Sign out" button is rendered in the bottom-right corner when auth is enabled and the visitor is signed in (not on the login page); on phones it sits in the status-badge row at the top, hidden while typing. With `LEAF_ALLOW_REMOTE`, the login page shows the 🌐 remote-access badge in its form's heading row (it has no breadcrumb for the badge to sit beside).
- **Users** (`[user …]` sections in `.leaf/config`, `docs/spec/users.md`) replace the one password: each signs in with a name and a password kept only as a PBKDF2 hash; the session cookie names the user and is valid only while they are a user and their password is the one it was signed in with (`passwordStamp`; the wiki's password likewise); a wrong name costs the same time as a wrong password. A wiki password or MCP token together with users refuses to start.
- **The settings file** `.leaf/config` holds password hashes and MCP tokens, the tokens only as SHA-256 hashes (`tokenMatches`): it is committed (the rest of `.leaf/`, the session key above all, stays out of git, also before a new wiki's first commit), but Leaf never shows it (`canSeePath` is false for `.leaf/`, which also holds the editor's texts left in conflict, `.leaf/drafts/<user>/`, shown only to their user in their editor: no history view, uncommitted list or MCP tool; `safePath` refuses it to every page route), written owner-only (0600) by `leaf user`/`leaf config`, and Leaf logs a warning when others may read it. A reload with an error keeps the settings from before (a broken edit neither locks everyone out nor opens the wiki), and so does removing the file while Leaf runs; `GET /api/health` (no login, for the healthcheck) then answers 503 with the error, which never repeats a password or token, and which it gives only with a session (or in a wiki without a login): it may name users, so without one the answer points to the log. Reloading in `docs/spec/users.md`.
- **Private pages and tasks** (with users, `private/<user>/`, tasks in `private/<user>/_deck/`, `docs/spec/users.md`): another user's are left out of every list, count and search and are 404 when opened directly, also when they don't exist (`refusePage`; an unknown task id likewise), so nothing tells what is in someone's folder. The rules are `go/access.go` alone (`canSee`, `canWrite`, `canSeePath`, `canSeeTask`); `tests/test_privacy.py` probes every route and MCP tool for leaks, and fails for a new one that isn't probed. Private is hidden inside Leaf, not encrypted: the files, git history and a git remote hold everything.
- `/mcp` requires an MCP token, `mcp-token` in the settings file (a bearer token, kept there as its hash; with users, a user's own, and the tools act as that user): without one set it is off (403), whether or not a password is set, because its tools write pages and tasks. Don't make it open again (see Auth in `docs/spec/mcp.md`).
- **Leaf's own folders are not served**: `.leaf/` (the session key, the settings file, the semantic cache), `.git/`, `_deck/` and every other folder starting with `_` or `.` hold no pages, and `safePath()` refuses slugs in them, so no page route reads or writes there (Routes in `docs/spec/routes.md`). Uploads are served only from `_assets/` by name (`/_assets/<filename>`, and `/private/<user>/_assets/<filename>` to that user only), the client code only from `public/`.
- The request checks around every route (`checks` in `go/server.go`) first validate the `Host` header (`hostAllowed`) against `allowedHosts` (`localhost:5000`, `127.0.0.1:5000`) plus the names in `hosts` (the settings file; comma-separated, compared without port and case, `hostName`), defeating DNS rebinding attacks. `LEAF_ALLOW_REMOTE=1` (in `.env`) without `hosts` skips the check (LAN access by IP); with `hosts` set the check stays on. Behind a reverse proxy on the same host, `hosts` alone is enough (the port stays on loopback).
- **Scripts in pages don't run** (`pageCSP`): every response carries `Content-Security-Policy: script-src 'self'; object-src 'none'; base-uri 'self'; form-action 'self'; frame-ancestors 'self'`. Pages render their raw HTML as written, and pages are also written by AI clients over MCP, which may have read a prompt injection in a mail or a web page: a `<script>`, an `onerror=` handler or a `javascript:` link in a page would otherwise run with the user's session and could read, rewrite or send away the whole wiki. Under `script-src 'self'` without `'unsafe-inline'`/`'unsafe-eval'` only Leaf's own script files run (Leaf has no inline scripts, `on…=` handlers or `eval`; the browser tests fail on any CSP violation of Leaf's own pages, see `docs/spec/testing.md`); this holds in the editor preview and the search preview too, which insert rendered HTML with `innerHTML`. `object-src 'none'`: no plugins; `base-uri 'self'`: no `<base>` that re-points Leaf's relative script paths; `form-action 'self'`: no form in a page that posts elsewhere. The rest of a page's HTML (images, links, iframes, styles) stays allowed. `X-Content-Type-Options: nosniff` on every response, so no JSON or text response runs as a script, and uploads not shown inline go out as `application/octet-stream` (`serveUpload`), so an uploaded `.js` can't be loaded by `<script src>` either, as `script-src 'self'` trusts Leaf's own origin.
- **Regexes from AI clients can't hang the server**: `grep_wiki` runs `git grep` in its own process, killed after 10 s; `replace_in_pages` matches with Go's RE2, which takes time linear in the text (no backtracking, so no lookarounds or backreferences). `replace_in_pages` in `docs/spec/mcp.md`.
- **Clickjacking**: `frame-ancestors 'self'` in that policy (added to an existing one, e.g. an SVG upload's sandbox policy) and `X-Frame-Options: SAMEORIGIN` (`pageCSP`), so no other site can frame Leaf.
- **Self-hosting behind HTTPS**: the session cookie is `Secure` when the request came over HTTPS, Leaf's own or a proxy's `X-Forwarded-Proto: https` (`isHTTPS`); over plain http (localhost, LAN) it works as before. Wrong passwords and wrong MCP tokens are throttled per client (`Throttle`, `loginThrottle`/`mcpThrottle`, in memory): after 5 failures in a row each try waits 1 minute, doubling up to an hour, refused unchecked (429, the login page says how long; `/mcp` sends `Retry-After`); a success clears the client. The client (`clientKey`) is the remote address, or, when that is loopback/private (a proxy), the last `X-Forwarded-For` entry (the one the proxy appended). Secrets are compared as bytes (`sameSecret`), so non-ASCII passwords work.
- **Cross-site writes are refused** (`crossSite`, checked after the Host check): a POST/PUT/PATCH/DELETE whose `Origin` header names another site, or is `null` (sandboxed iframe), gets 403. Without it any web page could post a form to `localhost:5000` and delete or overwrite pages, or write deck tasks (the deck API parses text/plain bodies, which need no CORS preflight), and raw HTML in markdown would turn an overwrite into a stored script. Requests without `Origin` (curl, scripts) are allowed. Behind a reverse proxy the proxy must pass the original `Host` through, or same-origin writes would be refused.
- **No secrets in the repo**: `.env` (tokens, password) is gitignored. The pre-commit hook `.githooks/pre-commit` (on once per clone: `git config core.hooksPath .githooks`) runs gitleaks over the staged changes, with a local gitleaks or else `./run.sh leaks --pre-commit --staged` in the tools image; a leak (exit 3) refuses the commit, a scan that can't run only warns. For `commit -a` and `commit <path>` git hands the hook a temporary index (`GIT_INDEX_FILE`, a host path); `run.sh leaks` passes it into the container as a `/repo/…` path, so those changes are scanned too (an index outside the repo: exit 2, a warning). On the first run `run.sh` says it is building the tools image. In a git worktree only a local gitleaks can check (the container can't follow `.git`'s host path). CI's **leaks** job scans every commit (`./run.sh leaks`). gitleaks is a pinned release, checked against its published checksums in `Containerfile.tools`.
