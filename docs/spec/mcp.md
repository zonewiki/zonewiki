# MCP server

Part of Leaf's spec (see `AGENTS.md` for the index).

## MCP server

`POST /mcp` lets an LLM client (any MCP client) read and write the wiki and the deck through tools. Protocol in `src/mcp_server.py` (JSON-RPC, no Flask), route in `server.py` (`mcp_endpoint`), tools in `src/mcp_tools.py` (`mcp_call_tool`). MCP's Streamable HTTP transport, reduced to what tools need: each POST carries one message (or a batch) and is answered with plain JSON; notifications get 202; no event stream (GET → 405), no sessions. `initialize` echoes the client's protocol version when it is in `PROTOCOL_VERSIONS`, else the newest, and sends `instructions` (`INSTRUCTIONS`) telling the model what Leaf is, which tools find what, to call `leaf_help` for questions about Leaf itself, and how to write (search before creating a page, extend rather than duplicate, edit_page/append_to_page over rewriting, a summary per write, `read_guides` before drafting). **Offer to capture**: when the model researches something elsewhere (an issue tracker, chat, mail, code, the web) and finds a fact a wiki page on the topic lacks or contradicts, it offers to add it, naming the page and each fact in one line, once per answer, and writes only when the user agrees. So the wiki keeps up with what the user looks up, without the model writing on its own. The instructions stay short (about 1.3 KB, a test keeps them under 1.9 KB): Claude Code cuts a server's instructions at about 2 KB, so what every session needs comes first and the tools' descriptions carry the details; the wiki's guide is appended after them (below), cut there too, which is why the instructions point to `read_guides`.

A client registers `http://localhost:5000/mcp` with the HTTP transport and the header `Authorization: Bearer <LEAF_MCP_TOKEN>`.

**The wiki's guide**: the page `wiki-guide` (`GUIDE_SLUG`) holds the user's conventions for keeping the wiki: where things go, tags, page layouts, what stays private. Its text is appended to the `instructions` (`mcp_tools.mcp_instructions`, passed to `handle`, which asks for them only on `initialize`), after a line saying it wins over the general advice and that the model should offer to add conventions the user settles. So the model knows it before its first write, in every MCP client (a client-specific skill or rules file would reach only that client), and it is versioned and editable like any page. Read anew at each `initialize`: an edit shows from the next session. Over `_GUIDE_CHARS` (8000) it is cut, with a pointer to read_page, since the instructions stay in the model's context all session. Without the page, the instructions instead nudge the model to offer starting one when the user describes conventions. It never counts as an orphan (list_pages).

**Folder guides** (`_check_guides`): the user's instructions for writing the pages in a folder and its subfolders live in a `CLAUDE.md` or `AGENTS.md` in it (any case), the files coding assistants read, so one guide serves an assistant working on the files and one working through Leaf. `wiki-guide` and a `CLAUDE.md`/`AGENTS.md` at the root are the whole wiki's. The guides for a page (`_folder_guides`) are the root's, then each folder's on the way down to the page's. A line that is only `@other.md` is replaced by that page's text, relative to the guide's folder (`_guide_text`, Claude Code's import), at most 3 deep. An import that isn't a page of the wiki stays as written. A file already part of another guide is left out, so a root `CLAUDE.md` holding just `@wiki-guide.md` adds nothing. Empty guides don't count.

Every page write (write_page, edit_page, append_to_page, file_scratch_note (the target), rename_page (source and target, a folder too), delete_page, restore_page, replace_in_pages with `dry_run=false`) takes `guides`, a list of guide ids (a comma-separated string works too). A write to a page with a guide whose id isn't in the list is refused with nothing written. The refusal is a tool error starting "Nothing was written.", with the ids to pass for this write and the text of each missing guide, as `=== guide <slug> (id <id>) ===` (cut at `_FOLDER_GUIDE_CHARS`, 8000, with a pointer to read_page). An id is `<guide slug>:<8 hex>`, a SHA-256 of the guide's text with its imports. When the user changes a guide, its old id stops counting and the next write shows the new text. A write to a guide itself ends with its new id (`_guide_note`). `read_page` of a whole guide adds `guide id: <id>` to its header, since reading it is reading the guide (not for a guide that imports other pages, whose text the page doesn't show: it says to use read_guides). The gate is the backstop; read_guides is the way in: the model reads the guide before drafting, so the draft follows it, rather than drafting, being refused and writing it again. Why a gate and not the instructions: Claude Code cuts a server's `instructions` at about 2 KB, so a guide appended there may never reach the model. Attaching a guide to every result costs its tokens on every call, since the server keeps no sessions. A refusal costs one call and sends each guide once per conversation, before the write. Without guides nothing changes. Deck task writes are not gated.

A tool failure the model can fix (bad slug, empty query, text not found) is a result with `isError`, not a protocol error.

### Reading

Annotated `readOnlyHint`.

| Tool | Does |
|------|------|
| `search_wiki(query, limit=8, under)` | The most relevant **sections**, full text, best first, each with title › heading, slug, the page's last edit date (`edited:`, so the model can tell current notes from stale ones), a URL with the heading anchor and the page's file on the host (`file:`, see Links). Several may come from one page. Matching deck tasks are results too, ranked with the sections. `under` restricts it to a folder: pages whose slug is that prefix or below it (`in_folder`, case ignored; `tickets`, `tickets/` and `/page/tickets` alike, `_clean_folder`), and no tasks. `scratch` restricts it to scratch notes (`retrieve(…, scratch=True)`), no tasks either: "what did I jot down about X". A folder without pages is a tool error, so the model corrects it. With `LEAF_QUERY_LOG=1` each query is logged (Measuring retrieval in `search.md`). |
| `search_tasks(tag, status="open", query, limit=50)` | Deck tasks filtered by tag (comma = all must match, case-insensitive; a list is its tag) and status (`open`, `done` = completed or won't do, `all`), separate lists included. With a query, ranked by BM25 within the filter; without, open tasks by deadline, then start date, then title, done ones newest first. Starts with "Today is …" so the model can tell overdue from upcoming. |
| `read_page(slug)` | A page's slug, URL and host file (`file:`), then its raw markdown, frontmatter included, plus a list of the deck tasks its `[[task:…]]` references stand for, then its place in the link graph (`_page_links`): `Linked from (N): …`, the pages linking to it (`find_backlinks`, the page's Backlinks; the first 50 named, then "… and N more"), `Broken wikilinks (no such page): …` when it has any (`_missing_links`), and, with semantic search, `Related, not linked (close in meaning): …`: the page view's Related (`SEMANTIC.related`, its floor and its prose minimum), pages linked either way left out, so the model sees connections not written down yet. So the model sees where a page sits without reading other pages. With `heading`, only that section (`_section_lines`, the same match as append_to_page's `under_heading`: subsections included, headings in code fences don't count), with a `section: lines A–B of N` line in the header, numbered as grep_wiki numbers them; a missing heading is an error listing the page's headings. Task references and broken links are then the section's. Accepts a slug, `/page/<slug>`, a full URL, `<slug>.md` or the page name (`_mcp_page_slug`); `safe_path` keeps it inside the wiki. |
| `grep_wiki(pattern, ignore_case=false, under, limit=50)` | Every line of every page matching a regex, as `slug`, then `  <line>: <text>` under it (lines cut at 300 characters), with the total count and how many are shown. For exact text and all its occurrences (ticket ids, names, TODOs, a term to replace), where search_wiki ranks and returns at most 20 sections. Pages only: no tasks, nothing in `_` folders. `gitstore.grep_pages` runs `git grep --no-index -P` (Perl-style; `-E`, extended regexes, when git is built without PCRE, found out once) in its own process, uncommitted pages included, with a 10s timeout (`GREP_TIMEOUT`): a pattern that backtracks badly is killed rather than holding up the single server process, which Python's `re` couldn't be. A bad pattern or the timeout is a tool error. Without git, the pattern is matched as plain text and the result says so. |
| `list_pages(limit=100, under, orphans=false, scratch=false)` | `slug \| title \| edited date \| pages linking to it` (`all_backlink_counts`, the Backlinks rule), most recently edited first; `under` lists one folder, `scratch` only scratch notes ("Scratch notes, …"; none: "No scratch notes."). `orphans` keeps only pages no other page links to (`_is_orphan`), leaving out the home page, the deck's home and scratch notes, which the module switcher reaches; the search modal's "Unlinked only" filter keeps those. |
| `list_tags()` | `tag \| pages \| open tasks \| done tasks`, most used first: page frontmatter tags (`page_tags`) and the tags of every task (`deckstore.all_tasks`, archived ones included), lowercased; a deck list's name is marked `(a list)`. So the model reuses tags instead of inventing `back-end` next to `backend`. |
| `history(slug, version, since, under, limit=20)` | Git history, three ways. Without `slug`: recent commits across the wiki (`gitstore.git_log_all`: `when \| version \| message \| pages`, a page by its slug, `_deck/` files as "deck tasks"), from the day `since` (YYYY-MM-DD) or in a folder (`under`), after a line naming the files with uncommitted changes (`git_uncommitted_files`). With `slug`: that page's versions (`git_log`, across renames: `version \| when \| +added -removed \| message`), a deleted page's too, saying so, and saying when the page has uncommitted changes newer than the first one. With `slug` and `version`: what that version changed, as `git_diff` with the rename handling of the browser's Changes view. `(MCP)` in a message marks an assistant's change. Without git, a tool error. |
| `leaf_help(query, topic, heading, limit=5)` | Leaf's own documentation (`manual.py`), so the model answers how-to questions about Leaf (how to rename a deck's tabs, a setting, the query syntax) from the docs instead of guessing. The docs are `README.md` (topic `readme`) and `docs/spec/*.md` (topic = file name), all but `testing.md`; the `Containerfile` copies them next to the code, and `manual.docs_root` finds them there or in the checkout (`src/..`); without them the tool errors. With `query`, the best passages by BM25 (`manual.find`: sections split by `embed.chunk_sections` into pieces of at most `CHUNK_CHARS`, 1500, the doc's title, topic and heading weighted like a page title; the index is rebuilt when a doc file changes), each as `Title › heading` with its `topic:` and `heading:`. With `topic`, the whole doc (`deck.md` and the case of the name are accepted); with `heading` too, one section, as read_page's `heading` (`_section_lines`), a missing one an error naming the doc's headings. With neither, the list of topics with their `##`/`###` headings. The description tells the model the spec is written for developers, so it answers in what the user types or clicks. |
| `read_guides(slug, guides)` | The guides for a page (also a new one) or a folder (`messages/`, or a folder's name without the slash), or without `slug` the whole wiki's (`_read_guides`): each as `=== guide <slug> (id <id>) ===` and its text, the whole wiki's first, after a line with the ids to pass with writes. Ids in `guides` (ones the model already has) are named, not repeated. Reading them counts: a write with those ids goes through at once. Its description tells the model to call it before drafting anything meant for the wiki, and ends with the folders that have a guide and each guide's title (`mcp_tool_list`, built at each `tools/list` through `handle`'s `tools`; at most `_GUIDED_SHOWN`, 25, then "… and N more"), so the model knows from the start, before it writes a word, that `messages/` has instructions. Tool descriptions stay in the model's context like the instructions, but aren't cut at 2 KB. |
| `check_links(under)` | Every `[[wikilink]]` leading to no page, by page (`_missing_links`, the renderer's rule, code aside), each with the existing slug it was probably meant for (`difflib.get_close_matches` on the slug, cutoff 0.8). Wikilinks only, pages only. |

A task as the tools show it (`_mcp_task_text`) includes `id:`, its 8-character short id (`decksyntax.short_id`), which the task tools take and a page can use as `[[task:…]]`.

### Writing

The wiki is mostly written by LLMs, so they write through Leaf rather than to the files: each write is a git commit (no `/uncommitted` pile), a rename re-points links, and the result tells the model what it would otherwise have to look up. Every write tool takes an optional `summary`; the commit message is the action, then the summary, then `(MCP)` (`_commit_msg`: `Update tickets/bug-1: add findings (MCP)`, `Create deck task (MCP)`), so the history tells the model's changes from the user's. Tools that only add are annotated `destructiveHint: false`, those that change or remove `true`, so a client can ask before those. The token `/mcp` requires (below) guards writes as it guards reads, and git keeps every change undoable.

| Tool | Does |
|------|------|
| `write_page(slug, content, overwrite=false, summary)` | Creates a page. The slug may be a name (`Tickets/BUG 1234` → `tickets/bug-1234`, `to_slug`); folders starting with `_` or `.` are refused (`_new_slug` via `safe_path`: Leaf doesn't list or serve pages there). An existing page (`_mcp_page_slug`) is an error that points at edit_page/append_to_page, unless `overwrite`, which replaces its text. Content gets one trailing newline. A new page's result names up to five pages whose title or file name is close (`_similar_pages`: `difflib` ratio ≥ 0.8 on normalised titles and last slug parts), so the model notices when it should extend one instead. With semantic search it also names the three pages closest to it in content (`_close_in_content`, `SEMANTIC.related_to_text`: the new text's sections embedded at once, since the worker indexes the page later; pages it links to and those already named for a similar name left out), which a different name doesn't hide, with the advice to merge into one that covers the topic, else link them. **`scratch=true`** makes a scratch note instead (`_write_scratch`, `scratch.create`, as the browser's New scratch note): `slug` is then just its name in any words (`Alex prep`), and Leaf puts the date and time in front (`2026-10-15_09-30-00_alex-prep`; a `/` is a hyphen, and a second note of that name in the same second gets the next second). Without a `# Title` in the content (after any frontmatter) the name becomes it; without either it is an error. `overwrite` is an error (a scratch note is always new); the wiki's guide gates it as a page at the top level. The result says it is in Scratch, not the wiki, and names file_scratch_note. |
| `file_scratch_note(slug, name, folder, keep_date, page, heading, summary)` | The scratch note's two ⋯ actions (Scratch in `navigation.md`), through the same code (`scratch.move`, `scratch.append`), so the files, link updates and commit messages (`Promote …`, `Append …`, plus the summary and `(MCP)`) are the browser's. **`name`** (with `folder`, `keep_date`): Move to wiki, the new page at `promoted_slug(folder, name, date)`; the result reminds the model that nothing links to it yet (the browser's Link from, which opens an editor, has no MCP form). **`page`** (with `heading`, default `Title (YYYY-MM-DD)`, `scratch.append_heading`): Append to page, the note as a `## heading` section at the page's end, its tags into the page's, the note deleted, links to it pointing at the section; the result gives the section's URL. Exactly one of `name` and `page`. Refused: a slug that is no scratch note (pointing at rename_page/append_to_page), the browser's refusals (a taken name, one still a scratch name, a missing page, a heading the page already has). Uncommitted edits of the note and the page are committed first (`_save_pending`). Guides gate the target page. |
| `edit_page(slug, old_string, new_string, replace_all=false, edits, summary)` | Exact text replacement, the semantics of a coding agent's edit tool: `old_string` must occur once (else an error with the count) unless `replace_all`; not found is an error pointing at read_page. An empty `new_string` deletes. No read is needed first, so a passage from search_wiki can be edited directly; a concurrent change makes the match fail instead of being overwritten. `edits` (instead of `old_string`/`new_string`, not with them): a list of such replacements, each applied to the text the ones before it left (`_apply_edit`); one that fails is an error naming it (`Edit 2: …`) and nothing is written. One commit for all. |
| `replace_in_pages(find, replace, regex=false, ignore_case=false, include_code=false, under, dry_run=true, max_pages=50, limit=50, summary)` | Find and replace across pages, in one commit: a term, a name, a ticket prefix, a link spelled one way everywhere. Where it'd otherwise take grep_wiki plus an edit_page per page, or `sed` on the files and a commit by hand. `find` is matched within a line (`_replace_lines`), so it can't contain a line break (a passage spanning lines is edit_page's job); literal text, or with `regex` a Python regex whose groups `replace` names as `\1` or `\g<name>`. Code is left alone (fenced blocks, inline code spans; a match touching one stays) unless `include_code`; frontmatter isn't code. Pages only, not tasks; `under` limits it to a folder (an unknown one is an error). **By default a dry run**: nothing is written, and the result lists each changed line as `  <line>: - old` / `  <line>: + new` under its page (the first `limit` lines, cut as grep_wiki cuts them), so the model (or the user) checks it before calling again with `dry_run=false`. A write changing more than `max_pages` pages (at most 1000) is refused, with nothing written; the dry run says so beforehand. A write first commits the pages' uncommitted changes together as the user's `Save N pages` (`_save_pending_pages`), then commits `Replace '<find>' on N pages` (or on `<slug>` for one), and names the pages changed and any wikilinks the replacement made that lead nowhere. The regex runs in Python's `re` in the server process, unlike grep_wiki's: a pattern that backtracks badly could hold up a request. |
| `append_to_page(slug, content, under_heading, summary)` | Adds at the end of the page, or at the end of the section under a heading (`_append_at`: any level, compared as plain text without case and leading `#`s; the section ends before the next heading of its level or higher, headings in fenced code don't count; subsections belong to it). A missing heading is an error that lists the page's headings. For logs: no read of the page first. |
| `rename_page(slug, new_slug, summary)` | `gitstore.move_page`, as the editor's rename: links on pages and in tasks follow, all in one commit; the result says how many files changed. The home page can't be renamed, an existing target is an error. **A folder** moves too (`_rename_folder`, `gitstore.move_folder`): `slug` with a trailing slash (`tickets/`), or without one when no page has that name but pages are below it (`_folder_arg`; a page of the folder's name wins). Every page in it and its subfolders moves to `new_slug` + the rest of its slug, links to each following as for one page, all in one commit `Move <folder>/ to <new>/`, after the pages' uncommitted changes are committed as `Save <folder>/`. Refused, before anything moves: a target page that exists (all named), a folder into itself (`tickets` → `tickets/old`), a target in a `_`/`.` folder. Other files in the folder (images) stay where they are; subfolders left empty are removed. The result lists the moves (the first 20). |
| `delete_page(slug, summary)` | Deletes and commits (restorable from Deleted Pages); names the pages that still link to it. Not the home page. |
| `restore_page(slug, version, summary)` | Writes a version's text back (`git_show` at the page's path then, across renames) and commits `Restore <slug> to <sha>`, as the browser's Restore; a deleted page comes back the same way. The delete commit itself has no text (an error pointing at the version before it), a version the page already reads as is an error. |
| `create_task(title, notes, tags, due, start, repeat, repeat_every, repeat_from, keep, summary)` | A deck task through `deck.create_task`, the same code as `POST /api/deck`. `repeat`: daily/weekly/monthly/yearly/none; `repeat_every` 1–999. **A date is the deadline**: the field descriptions send a date the user gives the task ("tomorrow", "by Friday") to `due`, and `start` only to a stated start ("start Monday", "work on it tomorrow"); the model had put "for tomorrow" in start. **Tag hints** (`_tag_hints`), after the task: the tags of the `_SIMILAR_TASKS` (10) tasks most like it (BM25 over every task, open and done, by its title and notes) that it lacks, most common first, at most 5 (`Tags on similar tasks …: #home (2), …`), for the model to offer the user, since it can't see the deck; and its tags used by no other task or page (`New tags, used nowhere else yet: …`, pointing at list_tags), which are often near-duplicates (`meeting` beside `meetings`). Neither in a deck without tags. |
| `update_task(id, …same fields…, add_tags, remove_tags, status, summary)` | `deck.update_task`, as `PUT /api/deck/<id>`: only the given fields change; an empty `due`/`start`/`notes` clears it. `add_tags`/`remove_tags` work on the current tags (case ignored). `repeat_every`/`repeat_from` alone keep the task's repeat type. `status`: `done` (a keep task goes back to the pool; a repeating one spawns its next occurrence, shown in the result), `wont_do`, `skip` (won't do this occurrence, the series goes on), `open` (reopen; the spawned occurrence goes again unless it was changed since). Runs under the deck lock, so add/remove tags see the current tags. |
| `tag_tasks(ids, add_tags, remove_tags, summary)` | `deck.tag_tasks`, the function the `batch-tag` route uses: adds and removes tags on several tasks (open, completed, archived) in one commit, "Tag deck tasks". Case is ignored; a tag a task has keeps its spelling; a leading `#` is dropped. Ids as in `update_task`; an unknown or ambiguous one fails the whole call, before anything is written; at most 200 per call. The result says on how many tasks the tags changed (and that the others had them so already) and lists each task's tags. |
| `comment_task(id, text, summary)` | `deck.add_comment`: a dated status line. |
| `delete_task(id, summary)` | `deck.delete_task`; the tool's description steers the model to `status` done/wont_do instead. |

Pages are named as in read_page. A task `id` is its id or a prefix of it (`deckstore.find_tasks`: open, completed and archived tasks; an exact id wins; several matches are an error), and a `[[task:…]]` reference or a `/deck?task=…` link work too (`_task_arg`). The deck API's 400s (bad date, empty title, bad interval) come back as tool errors (`_deck_write`).

**Pages open in the editor**: the browser editor auto-saves to the file without committing (a commit comes with Done/Ctrl+S). A write tool that ran on such a page would take the user's draft into its own `(MCP)` commit, and an overwrite or delete would lose it, as it was never in git. So every page write first commits what the page holds uncommitted (`_save_pending`: `gitstore.is_uncommitted`, then `Save <slug>`, the message the Uncommitted list's commit gives), and the result says so: the user may have the page open. The editor's side is its own: each auto-save sends the hash of the text it last saw, so its next save after the model's write gets 409 and the editor shows "File was modified on disk" with Reload / Save my version instead of overwriting (see the auto-save points in `docs/spec/editor.md`).

**Wikilink check**: page writes end with a note naming the `[[wikilinks]]` the write *added* that lead to no page (`_missing_links` before and after, by the renderer's rule: the name as a slug, else slugified; code, `[[toc]]`, `[[deck]]` and `[[task:…]]` aside), so the model fixes a typo or creates the page. Links that were already broken are not repeated.

**Retrieval** (`retrieval.retrieve`) works on sections, not pages: an LLM needs the passages, and the best ones may share a page. BM25 runs over sections (`_page_chunk_docs`, the same `embed.chunk_sections` split, cached per page by mtime; `_chunk_index`), fused with `SEMANTIC.search_chunks` when semantic search is on (sections match by `embed.chunk_key`). Without semantic search it is keyword-only and still works. Deck tasks share that BM25 index (`deckstore.task_search_docs()`, each doc carrying its `task`), so they rank with sections, as in the browser search, and their semantic hits (`SEMANTIC.search_tasks`) join the section hits by similarity. `search_tasks` with a query fuses BM25 and semantic hits within its filter. A task is shown by `_mcp_task_text`: title, a line of facts (status, tags, start, due, repeat, keep, list), the `/deck?task=…` link (`task_href`), its notes and its comments.

**Links** in tool results start with `LEAF_BASE_URL` (e.g. `http://localhost:5000`, Leaf's address as your browser knows it) when set, else with the address the request came in on. A client in a container reaches Leaf as `host.containers.internal`, and links with that host don't open in the browser on the host. **File paths** (`file:`, `_host_file`: search_wiki's sections, read_page) are the host's wiki folder plus `<slug>.md` (a slug is the file's path relative to the wiki, unchanged): `LEAF_HOST_DATA`, which `run.sh` sets to `LEAF_DATA`'s host path, since inside the container the wiki is only `/wiki-data`; unset (no container), `LEAF_DATA` resolved. So a client on the host can open or edit the file directly. Tasks have none.

**Auth**: `/mcp` is exempt from the session login (`check_auth`), since an MCP client can't log in, and checks its own: it needs `LEAF_MCP_TOKEN`, sent as `Authorization: Bearer <token>` (compared in constant time, `_mcp_authorized`). Without a token set, `/mcp` is off: every request gets 403 with a hint to set one, with or without `LEAF_PASSWORD`. The tools write, so an open `/mcp` would let anything that reaches the port change the wiki; a token is never optional. A wrong or missing bearer gets 401 (`WWW-Authenticate: Bearer`); wrong tokens are throttled per client like wrong passwords (`MCP_THROTTLE`, its own count: after 5, 429 with `Retry-After`, waits doubling from 1 minute to an hour; see `docs/spec/security.md`). The Host and cross-site Origin checks apply as everywhere.
