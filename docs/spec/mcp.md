# MCP server

Part of Zone's spec (see `AGENTS.md` for the index).

## MCP server

`POST /mcp` lets an LLM client (any MCP client) read and write the wiki and the tasks through tools.
Protocol in `go/mcp.go` (JSON-RPC; the tool definitions as clients see them in `go/mcp_tools.json`),
route `mcpEndpoint`,
tools in `go/mcp*.go` (those that read in `mcptools.go`, that write pages in `mcpwrite.go` and `mcpreplace.go`, the task tools in `mcptasks.go`, guides in `mcpguides.go`),
each with what it writes in one table (`mcpToolTable`: nothing, tasks, or pages, which puts it under `pagesMu`; a tool that writes is refused to a viewer; a test holds the table against each definition's `readOnlyHint`, so a new writing tool can't be left out).
MCP's Streamable HTTP transport, reduced to what tools need: each POST carries one message (or a batch) and is answered with plain JSON; notifications get 202; no event stream (GET → 405), no sessions.
`initialize` echoes the client's protocol version when it is in `protocolVersions`,
else the newest,
and sends `instructions` (`mcpInstructions`) telling the model what Zone is,
which tools find what,
to call `zone_help` for questions about Zone itself,
and how to write (search before creating a page, extend rather than duplicate, edit_page/append_to_page over rewriting, a summary per write, `read_guides` before drafting).
**Offer to capture**: when the model researches something elsewhere (an issue tracker, chat, mail, code, the web) and finds a fact a wiki page on the topic lacks or contradicts, it offers to add it, naming the page and each fact in one line, once per answer, and writes only when the user agrees.
So the wiki keeps up with what the user looks up, without the model writing on its own.
The instructions stay short (about 1.3 KB, a test keeps them under 1.9 KB): Claude Code cuts a server's instructions at about 2 KB, so what every session needs comes first and the tools' descriptions carry the details;
the wiki's guide is appended after them (below), cut there too, which is why the instructions point to `read_guides`.

**Two ways in.**
With a login, a client is given only the address, `http://localhost:5000/mcp`: it opens the wiki in its user's browser, they sign in and allow it, and it gets tokens of its own (Connecting with OAuth, below).
Or a client registers the address with the HTTP transport and the header `Authorization: Bearer <token>`, a token that doesn't change, from the page **Connect an assistant** (below) or from `./run.sh config token` (with users, `./run.sh user token NAME`): for a client that can't open a browser, a script, or a wiki without a login.
Either way the assistant acts as the user whose token it is.

**Connect an assistant** (`/assistant`, `go/assistant.go`, `assistant.html`): the token made in the browser, without a shell on the host.
With users it is in the user menu ("Connect an assistant") and makes the token of whoever is signed in, never another user's (no field names one);
without users it makes the wiki's token, and anyone who can open the wiki can open it (the shortcuts dialog links to it in every wiki: "Connect an AI assistant").
A viewer may make one too: their assistant reads, and its writing tools are refused.

- **The page** says where a client connects (`/mcp` on `base-url`, else on the address the request came in on: `siteURL`), whether there is a token, and has two plain forms.
  It works without JavaScript.
  What is to be copied (the address at the top, a new token, the commands) is a line of its own with a **Copy** button (`.copy-line`, `js/copyline.js`; without JavaScript there is no button, and a click selects the line).
  The token's two actions are a row each: what there is ("Set" or "None") with Make a token, and Revoke.
- **Make a token** (`POST /assistant/token`): a new token (32 random bytes, as the commands make), kept as its hash in the settings file the way the admin page writes it (`changeSettings`, so every rule of the commands holds, and the log says "alice's MCP token (by alice)").
  It replaces the one before, which stops working.
  The answer to the POST shows it **once** (`Cache-Control: no-store`), with the line for Claude Code (`claude mcp add --transport http zone <url> --header "Authorization: Bearer <token>"`) and the header for any other client; a click selects each.
  The page never shows it again: lost, make a new one.
- **It takes the password again** (the user's own, or the wiki's; nothing to ask in a wiki without a login).
  A token outlasts the session it was made in, and signing out or a new password doesn't end it, so a session someone else got hold of mustn't be enough to make one.
  A wrong password is a 403 ("Incorrect password: no token was made."), and counts against the client as a wrong login does (`loginThrottle`: 429 with the wait), so the page guesses a password no faster than the login page.
- **Revoke the token** (`POST /assistant/revoke`, no password: it only ends access): the token is taken out of the settings file, the page says so (`?done=revoke`, said only when there is none), and `/mcp` answers 401 for it (403, off, when no token is left and OAuth is off).
- **Connections** (with OAuth): the page says how an assistant signs in (the address to paste; the line for Claude Code, `claude mcp add --transport http zone <url>`), and lists the assistants its user allowed: the name each gave, the host its answer went to, since when, the day it was last used, newest first.
  **End** (`POST /assistant/connections/<id>/revoke`, no password) ends one: its tokens are refused from then on (`?done=disconnect`); another user's is a 404.
  The static token is one per user and stays so: several assistants are several connections.

## Connecting with OAuth

`go/oauth.go`, `go/grants.go`, `oauth.html`.
What Claude's apps (web, Desktop, mobile: a "custom connector"), Claude Code and ChatGPT do with a remote MCP server: the user pastes the address of `/mcp`, a browser opens, they sign in to Zone and click Allow.
Zone is its own authorization server, on the same address, as the MCP authorization spec (2025-11-25) has it; nothing but Go's standard library.

- **Only with a login**: someone has to sign in and allow, so OAuth is on when the wiki has users or a password (`oauthOn`), and there is none in a wiki without a login (the routes below are a 404, `/mcp` answers as without it).
  `mcp-oauth = no` in the settings file turns it off: static tokens only, and the connections there are stop working until it is on again.
- **What reaches it**: an assistant that runs on its maker's servers (Claude's apps, ChatGPT) calls Zone from there, so the wiki must be on the internet over https (set `base-url` and `hosts`).
  One on the user's computer (Claude Code) reaches any wiki that computer does.
- **`/mcp` says where to sign in**: with OAuth on, a call without a token, or with a wrong one, is a `401` with `WWW-Authenticate: Bearer resource_metadata="<address>/.well-known/oauth-protected-resource/mcp", scope="mcp"` (a wrong one also `error="invalid_token"`), whether or not a static token is set.
  A call with no `Authorization` header at all is no guess and isn't counted against the client (a client finding its way); a wrong token is, as ever.
- **The metadata** (no login needed): `GET /.well-known/oauth-protected-resource/mcp` and `/.well-known/oauth-protected-resource` (RFC 9728: `resource`, the address of `/mcp`; `authorization_servers`, Zone's own address) and `GET /.well-known/oauth-authorization-server` (RFC 8414: the endpoints below, `code_challenge_methods_supported: ["S256"]`, `token_endpoint_auth_methods_supported: ["none"]`).
  The addresses are on `base-url`, else on the address the request came in on (`siteURL`): behind a proxy set `base-url`, or `resource` won't be the address the user typed and the client refuses it.
- **Registration** (`POST /oauth/register`, RFC 7591; no login, any origin): a client sends its `client_name` and `redirect_uris` and gets a `client_id`. Public clients only: there is no secret.
  Zone keeps nothing: the client id *is* the name and the redirect URIs, signed with Zone's key (`.zone/secret_key`; `oauthClient.id`, `clientOf`), so strangers calling the endpoint leave nothing behind, and a client id Zone didn't sign is no client.
  A redirect URI is `https`, or `http` on `localhost`, `127.0.0.1` or `[::1]` (a program on the user's computer, RFC 8252), without a fragment or a user; one to ten of them (**400** `invalid_redirect_uri`).
  Other schemes (`cursor://` …) are refused for now.
  Client ID Metadata Documents aren't offered yet (the metadata doesn't advertise them, so clients register): they would have Zone fetch an address a stranger names.
- **The question** (`GET /oauth/authorize`, signed in: anyone else goes through the login and comes back, the question kept in `next`): the page says who asks (the name the client gave: it is only a claim), where the answer goes (the redirect URI's host), as whom the assistant will act ("as you, alice: it will see and change what you do, no more"; a viewer's reads only), and for an address on this computer that any program on it could ask in this name. **Allow** and **Deny**.
  - Before anything is shown, the client id and the redirect URI are checked: one Zone doesn't know is a page saying so (**400**), never a redirect. The answer goes only where the registration said: that address exactly, or for a program on this computer the same address at whatever port.
  - What else the client got wrong (no `response_type=code`, no PKCE challenge with `S256`, a `resource` that isn't this wiki's `/mcp`) is a page too (400), with a link back that tells the client (`error=…`).
  - **Allow takes the password again** (`POST /oauth/authorize`), as making a token does and for the same reason: a connection outlasts the session, so a session someone else got hold of mustn't be enough.
    A wrong one is a 403 ("Incorrect password: nothing was allowed.") and counts against the client as a wrong login (`loginThrottle`: 429).
    The POST is behind the Origin check as every form.
  - **The answer is a page, not a redirect**: "Connected", with a `Refresh` header that sends the browser on to the client (`<redirect_uri>?code=…&state=…&iss=…`) and the same address as a link.
    The page policy lets a form lead only to Zone itself (`form-action 'self'`), and browsers hold a form's redirects to that, so a redirect would be blocked; this way the policy stays as it is. Deny goes back the same way with `error=access_denied`.
  - The code is 32 random bytes, kept in memory as its hash for a minute, for one use (`authCodes`; a restart drops the few that are open).
- **Tokens** (`POST /oauth/token`, form-encoded; no login, any origin): `grant_type=authorization_code` with the `code`, its `code_verifier` (PKCE, S256), the same `client_id` and `redirect_uri`; or `grant_type=refresh_token` with the `refresh_token` and `client_id`.
  The answer: an `access_token` (an hour), a `refresh_token`, `token_type: Bearer`, `scope: mcp`.
  - Both are 32 random bytes and Zone keeps only their hashes, as of a static token; not JWTs, so ending a connection takes effect at once.
  - **A refresh token works once**: each use gives a new pair, and the access token before stops working. Unused for 90 days it expires, and the connection with it.
    One used a second time was copied (the client, or a thief, has a newer one): the connection is ended and the log says so. A client that lost an answer to a refresh therefore has to connect again.
  - A refresh token is its client's: another client id gets nothing.
  - What gets none is a **400** with `error`: `invalid_grant` (a code wrong, used, older than a minute, for another client or redirect URI, the wrong verifier; a refresh token wrong, used, expired or revoked; a user who can't sign in any more), `invalid_client`, `invalid_target` (another `resource`), `unsupported_grant_type`.
    Failures count against the client as wrong MCP tokens do (`mcpThrottle`: **429** with `Retry-After`).
- **One scope**, `mcp`: what an assistant may do is its user's role, as with a static token.
- **Connections are kept** in `.zone/grants` (`grants.go`): the id, the user ("" in a wiki without users: the wiki's), the client's name, the hash of its client id, the redirect host, when it was made, the day it was last used, the token hashes and when they expire.
  Owner-only (0600), written whole, one change at a time (`changeGrants`: a lock in the process and `lockFile` on `.zone/grants.lock`, as a command writes it too), not committed (state, like `.zone/links`), read again when the file changed (`readGrants`).
  Not in the settings file: tokens change by the hour, and a change there is a change of the settings.
- **What ends a connection**: End on Connect an assistant; its refresh token expiring or being used twice; its user being removed (the Users tab, `zonewiki user remove`); its user setting a new password by a **reset link** (they may have lost the account to someone; the welcome page says so).
  A disabled user's are refused while they are disabled, and work again after.
  An ordinary new password (Change password, `zonewiki user passwd`) leaves them, as it leaves a static token.
- **Not yet**: Client ID Metadata Documents, CORS for clients that run in a browser, a read-only connection for an editor, `/oauth/revoke` (a client's "disconnect" doesn't end the connection in Zone: End does). Tested against real clients so far: Claude (`docs/plans/mcp-oauth.md`, phase 3).
- Tests: `tests/test_oauth.py` plays the client over HTTP; `tests/e2e/test_oauth.py` holds that Allow and Deny get the browser back to the client under the page policy.

**The wiki's guide**: the page `wiki-guide` (`guideSlug`) holds the user's conventions for keeping the wiki: where things go, tags, page layouts, what stays private.
Its text is appended to the `instructions` (`mcpInstructions`, passed to `handle`, which asks for them only on `initialize`), after a line saying it wins over the general advice and that the model should offer to add conventions the user settles.
So the model knows it before its first write, in every MCP client (a client-specific skill or rules file would reach only that client), and it is versioned and editable like any page.
Read anew at each `initialize`: an edit shows from the next session.
Over `guideChars` (8000) it is cut, with a pointer to read_page, since the instructions stay in the model's context all session.
Without the page, the instructions instead nudge the model to offer starting one when the user describes conventions.
It never counts as an orphan (list_pages).

**Folder guides** (`checkGuides`): the user's instructions for writing the pages in a folder and its subfolders live in a `CLAUDE.md` or `AGENTS.md` in it (any case), the files coding assistants read, so one guide serves an assistant working on the files and one working through Zone.
`wiki-guide` and a `CLAUDE.md`/`AGENTS.md` at the root are the whole wiki's.
The guides for a page (`folderGuides`) are the root's, then each folder's on the way down to the page's.
A line that is only `@other.md` is replaced by that page's text, relative to the guide's folder (`guideText`, Claude Code's import), at most 3 deep.
An import that isn't a page of the wiki stays as written.
A file already part of another guide is left out, so a root `CLAUDE.md` holding just `@wiki-guide.md` adds nothing.
Empty guides don't count.

Every page write (write_page, edit_page, append_to_page, file_note (the target), rename_page (source and target, a folder too), delete_page, restore_page, replace_in_pages with `dry_run=false`, rename_task_tag and rename_task_list (the pages they change)) takes `guides`,
a list of guide ids (a comma-separated string works too).
A write to a page with a guide whose id isn't in the list is refused with nothing written.
The refusal is a tool error starting "Nothing was written.", with the ids to pass for this write and the text of each missing guide, as `=== guide <slug> (id <id>) ===` (cut at `folderGuideChars`, 8000, with a pointer to read_page).
An id is `<guide slug>:<8 hex>`, a SHA-256 of the guide's text with its imports.
When the user changes a guide, its old id stops counting and the next write shows the new text.
A write to a guide itself ends with its new id (`guideNote`).
`read_page` of a whole guide adds `guide id: <id>` to its header, since reading it is reading the guide (not for a guide that imports other pages, whose text the page doesn't show: it says to use read_guides).
The gate is the backstop; read_guides is the way in: the model reads the guide before drafting, so the draft follows it, rather than drafting, being refused and writing it again.
Why a gate and not the instructions: Claude Code cuts a server's `instructions` at about 2 KB, so a guide appended there may never reach the model.
Attaching a guide to every result costs its tokens on every call, since the server keeps no sessions.
A refusal costs one call and sends each guide once per conversation, before the write.
Without guides nothing changes.
Task writes are not gated.

A tool failure the model can fix (bad slug, empty query, text not found) is a result with `isError`, not a protocol error.

**Size of the tool list**: every session loads all tool definitions (about 24 KB),
so text is said once: the parameters many tools share (`summary`, `guides`) have one-line descriptions,
`read_guides` explains the guide gate,
and `update_task`'s `due`/`start` refer to `create_task`'s,
which carry the date rules.
A test keeps the total under 25,000 characters.

### Reading

Annotated `readOnlyHint`.

| Tool | Does |
|------|------|
| `search_wiki(query, limit=8, under)` | The most relevant **sections**, full text, best first, each with title › heading, slug, the page's last edit date (`edited:`, so the model can tell current notes from stale ones), a URL with the heading anchor and the page's file on the host (`file:`, see Links). Up to three may come from one page (`sectionsPerPage` in `search.md`). Matching tasks are results too, ranked with the sections. `under` restricts it to a folder: pages whose slug is that prefix or below it (`inFolder`, case ignored; `tickets`, `tickets/` and `/page/tickets` alike, `cleanFolder`), and no tasks. `notes` restricts it to notes (`retrieve(…, quicknote=true)`), no tasks either: "what did I jot down about X". A folder without pages is a tool error, so the model corrects it. With `query-log = yes` in the settings file each query is logged (Measuring retrieval in `search.md`). |
| `search_tasks(tag, list, assignee, status="open", query, order="deadline", limit=50)` | Tasks filtered by tag (comma = all must match, case-insensitive), by `list` (the tasks in that list; a list is no tag) and status (`open`, `closed` = done or won't do, `all`), separate lists included. With users, `assignee` narrows it to a user's tasks, read as an embed's `assignee=` (`assigneeParamMatches`): `me` (the assistant's user: "my tasks"), a user name, `none`, `a\|b`, `-a`; without users it is a tool error. With a query, ranked by BM25 within the filter; without, open tasks by deadline, then start date, then title, done ones newest first. `order="manual"` lists the open ones in the user's own order instead (`sort_order`, the Open view's Sorted section, top first: their priority), the tasks not yet ranked after them, newest first (`manualBefore`; the Open view shows those above, as they wait to be ranked). Starts with "Today is …" so the model can tell overdue from upcoming. |
| `read_page(slug)` | A page's slug, URL and host file (`file:`), its hash (`hash:`, the whole file's, also when reading a section; kept as a base for merges, `keepBase`, for write_page's `base_hash`), then its raw markdown, frontmatter included, plus a list of the tasks its `[[task:…]]` references stand for, then its place in the link graph (`pageLinks`): `Linked from (N): …`, the pages linking to it (`findBacklinks`, the page's Backlinks; the first 50 named, then "… and N more"), `Broken links (no such page): …` when it has any (`missingLinks`), and, with semantic search, `Related, not linked (close in meaning): …`: the page view's Related (`related`, its floor and its prose minimum), pages linked either way left out, so the model sees connections not written down yet. So the model sees where a page sits without reading other pages. With `heading`, only that section (`sectionLines`, the same match as append_to_page's `under_heading`: subsections included, headings in code fences don't count), with a `section: lines A–B of N` line in the header, numbered as grep_wiki numbers them; a missing heading is an error listing the page's headings. Task references and broken links are then the section's. Accepts a slug, `/page/<slug>`, a full URL, `<slug>.md` or the page name (`mcpPageSlug`); `safePath` keeps it inside the wiki. |
| `grep_wiki(pattern, ignore_case=false, under, limit=50)` | Every line of every page matching a regex, as `slug`, then `  <line>: <text>` under it (lines cut at 300 characters), with the total count and how many are shown. For exact text and all its occurrences (ticket ids, names, TODOs, a term to replace), where search_wiki ranks and returns at most 20 sections. Pages only: no tasks, nothing in `_` folders. `grepPages` runs `git grep --no-index -P` (Perl-style; `-E`, extended regexes, when git is built without PCRE, found out once) in its own process, uncommitted pages included, with a 10s timeout (`grepTimeout`): a pattern that backtracks badly is killed rather than holding up the single server process, which Python's `re` couldn't be. A bad pattern or the timeout is a tool error. Without git, the pattern is matched as plain text and the result says so. |
| `list_pages(limit=100, under, orphans=false, notes=false)` | `slug \| title \| edited date \| pages linking to it` (`allBacklinkCounts`, the Backlinks rule), most recently edited first; `under` lists one folder, `notes` only notes ("Notes, …"; none: "No notes."). `orphans` keeps only pages no other page links to (`isOrphan`), leaving out the home page, the default list's page and notes, which the module switcher reaches; the search modal's "Unlinked only" filter keeps those. |
| `list_tags()` | `tag \| pages \| open tasks \| done tasks`, most used first: page frontmatter tags (`mdtext.PageTags`) and the tags of every task (`allTasks`, archived ones included), lowercased; then the task lists the user sees, apart (`mcpListsText`: each with its open tasks, whether it is private, and which is the default list), since a list is where a task is and no tag. So the model reuses tags instead of inventing `back-end` next to `backend`. |
| `history(slug, version, since, under, limit=20)` | Git history, three ways. Without `slug`: recent commits across the wiki (`gitLogAll`: `when \| version \| message \| pages`, a page by its slug, `_tasks/` files as "tasks"), from the day `since` (YYYY-MM-DD) or in a folder (`under`), after a line naming the files with uncommitted changes (`gitUncommittedFiles`). With `slug`: that page's versions (`gitLog`, across renames: `version \| when \| +added -removed \| message`), a deleted page's too, saying so, and saying when the page has uncommitted changes newer than the first one. With `slug` and `version`: what that version changed, as `gitDiff` with the rename handling of the browser's Changes view. `(MCP)` in a message marks an assistant's change. Without git, a tool error. |
| `zone_help(query, topic, heading, limit=5)` | Zone's own documentation (`go/manual.go`), so the model answers how-to questions about Zone (how to rename a task list's tabs, a setting, the query syntax) from the docs instead of guessing. The docs are `README.md` (topic `readme`) and `docs/spec/*.md` (topic = file name), all but `testing.md`; the `Containerfile` copies them next to the browser code (`/app/public`), and `docsRoot` finds them there or in the checkout; without them the tool errors. With `query`, the best passages by BM25 (`manualFind`: sections split by `chunkSections` into pieces of at most `manualChunkChars`, 1500, the doc's title, topic and heading weighted like a page title; the index is rebuilt when a doc file changes), each as `Title › heading` with its `topic:` and `heading:`. With `topic`, the whole doc (`tasks.md` and the case of the name are accepted); with `heading` too, one section, as read_page's `heading` (`sectionLines`), a missing one an error naming the doc's headings. With neither, the list of topics with their `##`/`###` headings. The description tells the model the spec is written for developers, so it answers in what the user types or clicks. |
| `read_guides(slug, guides)` | The guides for a page (also a new one) or a folder (`messages/`, or a folder's name without the slash), or without `slug` the whole wiki's (`readGuides`): each as `=== guide <slug> (id <id>) ===` and its text, the whole wiki's first, after a line with the ids to pass with writes. Ids in `guides` (ones the model already has) are named, not repeated. Reading them counts: a write with those ids goes through at once. Its description tells the model to call it before drafting anything meant for the wiki, and ends with the folders that have a guide and each guide's title (`mcp_tool_list`, built at each `tools/list` through `handle`'s `tools`; at most `guidedShown`, 25, then "… and N more"), so the model knows from the start, before it writes a word, that `messages/` has instructions. Tool descriptions stay in the model's context like the instructions, but aren't cut at 2 KB. |
| `read_file(url)` | An upload a page or task links to, by the link's target (Files, below): an image as an image, a text file as its text. |
| `check_links(under)` | Every link leading to no page, by page: `[[wikilinks]]` (`missingLinks`, the renderer's rule) and markdown links that resolve to a page slug (relative to the page's folder, `/page/` links too; `mdLinkMisses`; external links, anchors, folders and files such as `_assets/` aside), code aside. Each comes with the existing slug it was probably meant for (`difflib.get_close_matches`, cutoff 0.8). Writes name the new ones in a note in the same form. |

A task as the tools show it (`mcpTaskText`) includes `id:`, its 8-character short id (`shortID`), which the task tools take and a page can use as `[[task:…]]`.

### Writing

The wiki is mostly written by LLMs, so they write through Zone rather than to the files: each write is a git commit (no `/uncommitted` pile), a rename re-points links, and the result tells the model what it would otherwise have to look up.
Every write tool takes an optional `summary`; the commit message is the action, then the summary, then `(MCP)` (`commitMsg`: `Update tickets/bug-1: add findings (MCP)`, `Create task (MCP)`), so the history tells the model's changes from the user's.
Tools that only add are annotated `destructiveHint: false`, those that change or remove `true`, so a client can ask before those.
The token `/mcp` requires (below) guards writes as it guards reads, and git keeps every change undoable.

| Tool | Does |
|------|------|
| `write_page(slug, content, overwrite=false, summary)` | Creates a page. `content`'s description gives the frontmatter's format and keys (`tags`, `tldr`, `sources`; see Frontmatter in `rendering.md`), since a model writing a page otherwise learns them only from pages it has read. The slug may be a name (`Tickets/BUG 1234` → `tickets/bug-1234`, `mdtext.ToSlug`); folders starting with `_` or `.` are refused (`newSlug` via `safePath`: Zone doesn't list or serve pages there). An existing page (`mcpPageSlug`) is an error that points at edit_page/append_to_page, unless `overwrite`, which replaces its text. **`base_hash`** (with `overwrite`; read_page's `hash:`): if the page changed since the model read it (the user edited it meanwhile), the model's text is merged with that change as the editor's saves are (`mergeWrite`, `mergeText`; Merge on save in `editor.md`), and the result says it merged; where both changed the same lines nothing is written, and the error shows only the clashing blocks with git's markers (`conflictBlocks`); a hash Zone no longer keeps (a restart) or no git: nothing written, read it again. Without `base_hash`, an overwrite replaces whatever the page holds (what it held uncommitted committed first, as below). Content gets one trailing newline. A new page's result names up to five pages whose title or file name is close (`similarPages`: `difflib` ratio ≥ 0.8 on normalised titles and last slug parts), so the model notices when it should extend one instead. With semantic search it also names the three pages closest to it in content (`closeInContent`, `relatedToText`: the new text's sections embedded at once, since the worker indexes the page later; pages it links to and those already named for a similar name left out), which a different name doesn't hide, with the advice to merge into one that covers the topic, else link them. **`note=true`** makes a note instead (`writeQuicknote`, `quicknote.create`, as the browser's New note): `slug` is then just its name in any words (`Alex prep`), and Zone puts the date and time in front (`2026-10-15_09-30-00_alex-prep`; a `/` is a hyphen, and a second note of that name in the same second gets the next second). Without a `# Title` in the content (after any frontmatter) the name becomes it; without either it is an error. `overwrite` is an error (a note is always new); the wiki's guide gates it as a page at the top level. The result says it is in Notes, not the wiki, and names file_note. |

Pages are named as in read_page.
A task `id` is its id or a prefix of it (`findTasks`: open, closed and archived tasks; an exact id wins; several matches are an error), and a `[[task:…]]` reference or a `/tasks?task=…` link work too (`_task_arg`).
The tasks API's 400s (bad date, empty title, bad interval) come back as tool errors (`tasksWrite`).

**Pages open in the editor**: the browser editor auto-saves to the file without committing (a commit comes with Done/Ctrl+S).
A write tool that ran on such a page would take the user's draft into its own `(MCP)` commit, and an overwrite or delete would lose it, as it was never in git.
So every page write first commits what the page holds uncommitted (`keepPending` in `go/pageops.go`: `isUncommitted`, then `Save <slug>`, the message the Uncommitted list's commit gives; by the user who auto-saved it, with users, else Zone), and the result says so: the user may have the page open.
The browser's writes that replace or remove a page's text (delete, restore, rename, Keep mine, Reload theirs) do the same, through the same function.
The editor's side is its own: each auto-save sends the hash of the text it last saw,
so its next save after the model's write is merged with it (the user's textarea gets the model's change),
or,
where both changed the same lines,
refused with the banner (Reload theirs, Keep mine, Merge by hand) instead of overwriting (Merge on save in `docs/spec/editor.md`).

**Wikilink check**: page writes end with a note naming the `[[wikilinks]]` the write *added* that lead to no page (`missingLinks` before and after, by the renderer's rule: the name as a slug, else slugified; code, `[[tasks:]]` and `[[task:…]]` aside), so the model fixes a typo or creates the page.
Links that were already broken are not repeated.

**Retrieval** (`retrieve`) works on sections, not pages: an LLM needs the passages, and the best ones may share a page.
BM25 runs over sections (`_page_chunk_docs`, the same `chunkSections` split, cached per page by mtime; `chunkIndex`), fused with `searchChunks` when semantic search is on (sections match by `chunkKey`).
Without semantic search it is keyword-only and still works.
Tasks share that BM25 index (`taskSearchDocs()`, each doc carrying its `task`), so they rank with sections, as in the browser search, and their semantic hits (`searchTasks`) join the section hits by similarity.
`search_tasks` with a query fuses BM25 and semantic hits within its filter.
A task is shown by `mcpTaskText`: title, a line of facts (status, private, tags, with users `assigned to: <name>` (marked when it is the user, or someone who can no longer be given tasks), importance when it isn't normal, start, due, repeat, keep, list), the `/tasks?task=…` link (`taskHref`), its description and its comments.
The tools call a task's text `description`, as the task's file and the edit dialog do; `notes`, its name in the tools before, is refused with a message saying so (an argument a tool doesn't know is otherwise dropped without a word, and an assistant's tool list may be older than the server).

### Files

Uploads (`_assets/`, File paste and drag & drop in `docs/spec/editor.md`) are read and added by assistants too (`go/mcpfiles.go`), in two ways, since a file that passes through a tool call is in the model's context whole.

- **`read_file(url)`**: `url` is a link's target as a page or task has it (`/_assets/photo.png`, percent-encoded or not, with or without the wiki's address before it; `uploadFile`).
  A PNG, JPEG, GIF or WebP up to 4 MB comes as an image the model sees (a second content part, `{"type": "image", "data": <base64>, "mimeType": …}`, after a line naming the file, its type and size);
  a text file (anything that is valid UTF-8 without NUL bytes: `.txt`, `.csv`, `.md`, `.json`, SVG …) as its text, cut off after 200 KB;
  anything else (a PDF, an archive) or a bigger image is only named, with how to fetch it over HTTP.
  Only uploads are read: a shared one, or with users one of the user's own private ones (another user's is "No such file", as one that isn't there); no path leaves `_assets/`, and dot files aren't files.
- **`upload_file(filename, text | content_base64, page)`**: a text file from `text`, any other from `content_base64` (line breaks and missing padding are fine), one of the two; at most 1 MB (`toolUploadMax`, or `upload-max` if that is less), and a bigger one is refused with how to send it over HTTP.
  The name is the last part of `filename` (no dot files); **a taken name gets a number** (`deck-2.pdf`, `freeUploadName`), so nothing is ever replaced: there is nobody to ask.
  `page`: with users, a file for a page in the user's private folder goes to `private/<user>/_assets/` and only they can open it; otherwise it is shared.
  The answer is the markdown that links it (`![name](url)` for an image, `[name](url)` otherwise, the URL percent-encoded), since an upload shows nowhere until a page or task links it.
  It is saved as the browser's upload is (`storeUpload`: `storage-max`, a commit "Upload <name> (MCP)" by the user), and a viewer doesn't have the tool.
- **Over HTTP with the token**, for an assistant with a shell and a file of any size: `POST /api/upload` (multipart, the field `file`, optionally `page`; the answer is `{"url": …}`) and `GET /_assets/<file>` or `/private/<user>/_assets/<file>` take the MCP token (or a connection's access token) as `Authorization: Bearer …` in place of a session (`tokenForFiles`, `tokenRequest` in the request checks).
  The token is checked as `/mcp` checks it: a wrong one is 401 and counts against the client (`mcpThrottle`); the request then runs as the token's user, so a viewer's upload is refused (403) and a private upload is its owner's.
  An upload sent this way takes a free name like the tool's, whatever `overwrite` says (`byToken`).
  The token opens these routes only: a page, the task API or any other route with a bearer token and no session goes to the login as ever.
  Both tools' refusals name the two `curl` commands (`fileRoutesHint`).

**Links** in tool results start with `base-url` from the settings file (e.g. `http://localhost:5000`, Zone's address as your browser knows it) when set, else with the address the request came in on.
A client in a container reaches Zone as `host.containers.internal`, and links with that host don't open in the browser on the host.
**File paths** (`file:`, `hostFile`: search_wiki's sections, read_page) are the host's wiki folder plus `<slug>.md` (a slug is the file's path relative to the wiki, unchanged): `ZONE_HOST_DATA`, which `run.sh` sets to `ZONE_DATA`'s host path, since inside the container the wiki is only `/wiki-data`;
unset (no container), `ZONE_DATA` resolved.
So a client on the host can open or edit the file directly.
Tasks have none.

**Auth**: `/mcp` is exempt from the session login (`checks`, `signedIn`),
since an MCP client can't log in,
and checks its own: it needs the wiki's MCP token (`mcp-token` in the settings file, kept as its hash: `tokenMatches`),
sent as `Authorization: Bearer <token>` (compared in constant time, `mcpAuthorized`).
With users (`docs/spec/users.md`) each user has their own token instead (`mcp-token` in their section),
and the tools act as the token's user: their writes are committed in that user's name,
`history` names authors,
and another user's private pages don't exist for them (Private pages and MCP in `docs/spec/users.md`).
Without a token set, `/mcp` is off: every request gets 403 with a hint to set one, with or without a password.
The tools write, so an open `/mcp` would let anything that reaches the port change the wiki; a token is never optional.
A wrong or missing bearer gets 401 (`WWW-Authenticate: Bearer`); wrong tokens are throttled per client like wrong passwords (`mcpThrottle`, its own count: after 5, 429 with `Retry-After`, waits doubling from 1 minute to an hour; see `docs/spec/security.md`).
The Host and cross-site Origin checks apply as everywhere.
