# Editor

Part of Leaf's spec (see `AGENTS.md` for the index).

## In-Browser Editor

- `/edit/<slug>` renders a split-pane view: `<textarea>` on the left, live preview on the right.
- Live preview updates as the user types (debounced, ~300ms) by calling `POST /api/preview`, which returns rendered HTML.
- **Very wide screens** (≥1800px): the preview pane may grow to 1100px (the writing pane keeps 800px); its text keeps the reading width (46rem), wide tables, code blocks and images alone in a paragraph use the rest.
- **Toolbar** — one line on every screen: the slug label shrinks with an ellipsis (full slug in its tooltip) and the buttons keep their size, so a long slug never pushes Done off-screen.
- **Formatting bar** (`templates/partials/format_bar.html`, `applyFormat` in `js/mdedit.js`; the deck's task notes have it too, without Make task, see Notes in `docs/spec/deck.md`): one line of buttons between the toolbar and the textarea, not WYSIWYG, just markdown help: bold (`**`), italic (`_`), strikethrough, heading (cycles `##` → `###` → none on the cursor's line; the H1 is the title), bulleted/numbered/checklist (on all selected lines, replacing another list marker; all of that kind already → removed; blank lines kept), quote, inline code, code block (fences the selected lines), table (a 2-column template after the current line), link (selected text → `[text]()` with the page autocomplete open; a selected URL → `[](url)`), wikilink (`[[selection]]`, or a bare `[[` that opens the autocomplete), task (`[[task:` after the cursor, opening the task completion), make task (see Task references), attach (file picker → the same upload as paste/drop, `uploadFileAtCursor`). Wraps toggle (markers inside or just outside the selection are removed) and keep surrounding spaces outside. **Ctrl+B / Ctrl+I / Ctrl+K** do bold, italic, link. Every change goes through `execCommand('insertText')` (`replaceRange`), so one Ctrl+Z undoes it and preview/auto-save follow as for typing. Buttons `preventDefault` on pointer/mouse down so the textarea keeps focus and selection (on a phone, the keyboard stays up). On narrow screens the bar scrolls sideways; under `(pointer: coarse)` the buttons are finger-sized.
- **Mobile editor** — on screens ≤640px the editor is not hidden; it becomes a full-screen stacked layout (textarea on top, preview below when toggled). The toolbar gains a **Preview** button (`#mobile-preview-btn`, class `mobile-only`) that calls the same `togglePreview()` as F2. The textarea font is 16px on mobile so iOS Safari doesn't zoom in on focus. Rename… and Delete move into a **⋯ dropdown** (`#editor-more-btn`, `.editor-more`) so the toolbar fits on one line; on wider screens `.editor-more` is `display: contents`, so the buttons stay inline.
- The editor textarea preserves tabs and disables spell-check.
- The textarea receives focus automatically on page load.
- **Auto-save while typing** — debounced ~2s after the user stops typing, the editor silently POSTs to `POST /api/save/<slug>`, which writes the file to disk (no git commit, no redirect). An unsaved-changes indicator (`●` dot in the toolbar) appears while there are unsaved changes and disappears when auto-save completes.
- **"Done" button** — POSTs to `POST /edit/<slug>`, which writes the file, creates a git commit, and redirects to `/page/<slug>`. This is the only editor action that commits. The toolbar has no Cancel button.
- **Auto-save on navigate away** — on the `pagehide` event, if the textarea content differs from the last auto-saved content, a `fetch(…, { keepalive: true })` POSTs to `POST /api/save/<slug>`. This silently preserves edits when the user follows a link or presses the back button (no git commit). Not `sendBeacon`: a page restored from the back/forward cache still gets the answer and its new file hash.
- **Saves run one at a time** (`queueSave` in `js/editor.js`: auto-save, Done/Ctrl+S, Enter on a wikilink, "Save my version"): each sends the file hash the previous save returned. Two in flight at once (a slow connection, or Done right after an auto-save started) both sent the older hash, and the second was refused with the "modified on disk" banner. Ctrl+S uses `requestSubmit()` so it goes through the same submit handler; `form.submit()` skipped it.
- **An AI assistant writing the open page** (MCP): its write tools first commit the draft the editor auto-saved, as the user's `Save <slug>` (see Pages open in the editor in `docs/spec/mcp.md`), so the draft is neither part of the assistant's commit nor lost to its overwrite. The editor's next save then carries a stale hash, gets 409, and shows the "modified on disk" banner: Reload from disk takes the assistant's version (what was typed since the last successful auto-save is lost), Save my version overwrites it (the assistant's commit stays in the history).
- **Section editing** — each rendered `<h2>`/`<h3>` has a ✎ button linking to `/edit/<slug>?section=N`. The editor loads only that section's text.
  - On GET, the server computes a `file_hash` (SHA-256 prefix) and the section's `(start_char, end_char)` character range within the full file, embedding them as hidden form fields.
  - On save (auto-save or Done), the server verifies the hash matches the current file, then does a direct string-slice replacement at `[start_char:end_char]`. If the file changed on disk (hash mismatch), the save is **rejected**: auto-save gets a 409 JSON error; Done redirects to a full-file editor with a conflict banner.
  - After each auto-save, the server returns updated `{ file_hash, start_char, end_char }` so the next auto-save uses fresh offsets.
  - The section's trailing blank lines are preserved on every splice (the editor loads the section with them stripped), including the conflict banner's "Save my version" (`force_section`), so the next heading never gets glued onto the section's last line.
  - This design avoids re-splitting the file on every save and eliminates the old index-based merge logic that could silently lose sections.
- **Undo** — all programmatic text insertions (list continuation, formatting bar, snippets, wikilink autocomplete, etc.) use `document.execCommand('insertText')` so they integrate correctly with the browser's native undo stack.

### Editor smart helpers

- **Wikilink autocomplete** (`linkAutocomplete` in `js/completion.js`, also used by the deck's task title and notes) — typing `[[` opens a dropdown of existing page slugs filtered as you type; `[text](` the same as `/page/` links; in the editor `[[task:` lists open deck tasks instead (see Task references). Arrow keys navigate, Enter or Tab inserts `[[slug]]` (it prevents the key's default, so the editor's own Enter/Tab handling skips it), Escape closes. Slugs are fetched once from `/api/pages`, shared by every field.
- **Emoji** (the same `linkAutocomplete`, so in the editor, the task title and the task Description): typing `:` and two letters (`:smi`) lists matching emoji, the exact name first, then names starting with it, names containing it, tags and descriptions (`:happy` finds 😀); Enter, Tab or a click inserts the **emoji character itself**, so the file holds 😄, not `:smile:`, and reads the same in any editor, in grep and on GitHub. A typed-out shortcode (`:tada:`) turns into its emoji as the closing colon is typed (an unknown name stays as typed). The list only opens after a space, the start of a line or an opening bracket, quote or `*_~>`, so `Note:`, `10:30` and `http:` don't open it, and not inside code (an open fence above the caret, or an odd number of backticks on the line). The names are GitHub's (gemoji v4.1.0, MIT, `public/vendor/gemoji/emoji.json`, as downloaded; to update it, replace the file with a newer release's), fetched the first time `:xx` is typed, then cached by the browser. Sharing mode doesn't hide this list (no page or task names in it).
- **Shared with the deck's task notes**: the editor's markdown helpers live in `js/mdedit.js` (`markdownEditor(textarea, opts)`): completion, the formatting bar and its shortcuts, snippets, list continuation, Enter on a selection, file paste/drop/attach, URL paste, and ticking a preview's checkbox (`toggleCheckboxInTextarea`). `js/editor.js` adds what only a page has: auto-save, the preview pane, Enter following a wikilink, Make task.
- **List continuation** (`continueList(textarea, e)`) — pressing Enter at the end of a list item (`- `, `* `, `1. `) inserts the next marker automatically (incrementing the number for ordered lists). Pressing Enter on an empty list item exits the list.
- **File paste and drag & drop** — pasting a file from the clipboard or dropping files onto the editor textarea uploads them via `POST /api/upload`. Images insert as `![name](url)`, other files as `[name](url)`.
- **URL paste** (`pasteUrlAsLink` in `js/util.js`, also used by the deck's task notes): pasting a bare URL over selected text makes `[selection](url)`; otherwise a prompt asks for a label (none, or cancel, inserts the plain URL, which autolinks on render). The insert goes through `execCommand('insertText')`, so Ctrl+Z undoes it; it once assigned `textarea.value` and wiped the undo history.
- **Snippets** — typing a trigger word then pressing Tab expands it inline. Built-in snippets: `/date` → `2026-03-22`, `/time` → `HH:MM`, `/datetime` → `2026-03-22 HH:MM`, all in local time (`localDate` in `js/util.js`; `toISOString()` would give UTC's day). Add more by extending the `snippets` object in `js/mdedit.js` (the deck's notes get them too).
- **Task list checkboxes** — `- [ ] task` and `- [x] task` render as interactive checkboxes in page view (rendered via `mdit-py-plugins` `tasklists_plugin` with `enabled=True`, so they are not disabled). Clicking a checkbox POSTs to `POST /api/toggle-checkbox/<path:slug>` with `idx` (0-based checkbox index), which toggles the `[ ]`/`[x]` in the `.md` file and returns 204. Ticking also records when: it appends `<!--d:YYYY-MM-DDTHH:MM:SS-->` (or adds ` d:…` to an existing `<!--t:<created>-->`), unticking takes it out again; the page shows these comments as small date chips (`render._render_task_dates`) (400 for a missing/non-integer/negative idx). In page view each toggle shows an **undo toast** ("Checked “…” · Undo"; undo is a second toggle). The toggle requests are chained (`toggleCheckboxOnServer`), so an undo can never overtake the toggle it reverts. In the editor, clicking a checkbox in the live preview edits the textarea via `execCommand('insertText')` (undoable, triggers preview/auto-save).
  - **Index mapping must match the renderer.** Only task-list items count: a list marker (`-`/`*`/`+`/`1.`/`1)`, optionally inside `>` blockquotes) followed by `[ ]`/`[x]`, whitespace and text. Fenced code and a leading frontmatter block are skipped; brackets in prose or later on the same line are not checkboxes. Server: `taskItemRE` / `taskItemLines()`; client: `taskItemRE` / `taskCheckboxOffsets()` in `js/page.js`. Keep the two in sync.
- **Checkbox list continuation** — pressing Enter at the end of a `- [ ] task` or `- [x] task` line inserts `- [ ] ` on the next line (always unchecked). Pressing Enter on an empty checkbox item (`- [ ] ` with no text) exits the list.

### Rename

- The editor toolbar includes a "Rename" button that reveals an inline rename form (hidden by default); the page view's ⋯ menu has **Rename…**, which opens a dialog (`#page-rename-dialog`) with the same form plus `from=page`.
- The form has a single text input pre-filled with the current slug, and a "Rename" submit button.
- On submit, POSTs to `POST /rename/<slug>` with field `new_name` (human-readable name accepted, converted to slug server-side).
- Server renames the file (`<old>.md` → `<new>.md`), re-points every link to it (see Links below), then redirects to `/page/<new-slug>`.
- Renaming `index` is forbidden — the server returns 400 if the old slug is `index`.
- If the new slug already exists, nothing is overwritten: the server redirects back with `?rename_error=…` (to the editor, which shows the rename bar with the error, or with `from=page` to the page view, whose rename dialog reopens with it). An unchanged name goes back the same way.
- Validate new slug with `safePath()` before renaming.

**Links** — when a page is renamed, every link to it is re-pointed (`rewritePageLinks()` via `updateReferences()`), so nothing that backlinks count is left broken:
- `[[Old Name]]` / `[[Old Name|Label]]` — matched by comparing the raw or slugified page name to the old slug; only the page-name part is replaced, the `|Label` is kept.
- Markdown links in the forms backlinks recognise: relative (`old`, `../dir/old`, `old.md`) and absolute (`/page/old`). Each keeps its style, `#anchor` and title; relative hrefs are recomputed from the linking page's directory. Images are never touched.
- Links inside fenced code and inline code are left alone (`maskCode`).
- **Moved pages keep their own links.** A page that moves into another folder (a rename into a folder, a folder move, a scratch note promoted into a folder) has its relative links re-based, through `rewriteMovedLinks()` (`rebaseLinks()` per page): each still reaches the same page or file from where the page is now, including links to other pages that moved too. Wikilinks name pages, so they only change when their target moves.

### File paste and drag & drop

In the editor, pasting a file from the clipboard or dropping a file onto the textarea automatically uploads it via `POST /api/upload`. All file types are accepted. Images are inserted as `![name](url)`; other files as `[name](url)`. Multiple files dropped at once are uploaded sequentially. The upload route uses the original filename when available (falling back to MIME-type guessing). If a file with that name already exists in `_assets/`, a numeric suffix is appended (`file-2.pdf`, `file-3.pdf`, …). The editor sends the page's slug along (`page`): with users, a file for a page in your private folder goes to `_assets/private/<you>/` and only you can open it (see `docs/spec/users.md`).
